### 2.1 M-16：handler 已写，但端到端仍不通（Major）

**车机实际载荷**（`CarrotUdpClient.kt:109-121`）：
```kotlin
fun sendControlCommand(cmd: String, action: LaneAction, vCruise: Int, overtakeMode: Int = 1) {
    ...
    put("arg", action.code)       // SPEED_LIMIT 时 action = LaneAction.KEEP
    put("v_cruise", vCruise)      // 真正的目标速度在这里
```
`RelayEngine.kt:188-192`：
```kotlin
udpClient.sendControlCommand(SPEED_LIMIT_COMMAND, LaneAction.KEEP, next)
```
→ `arg = "KEEP"`，`v_cruise = next`。

**C3 实际映射**（`amap_navi.py:1030-1035`）：
```python
self.shared_data.remote_cmd = "CANCEL" if c == "CANCEL_LANE_CHANGE" else c
self.shared_data.remote_arg = json_obj.get("direction") or json_obj.get("arg")
```
→ `remote_arg = "KEEP"`；`v_cruise` 从未被读取。

**handler 实际入参**（`carrot_serv.py:352-360`）：
```python
handler = command_handlers.get(self.carrotCmd)
if handler:
    handler(self.carrotArg)        # carrotArg == "KEEP"
```
`_handle_speed_limit_command("KEEP")` → `int("KEEP")` 抛 `ValueError` → 打印警告并 `return`。

**结论**：修复报告里的负向测试用的是 `arg="80"`，但**车机永远不会发 `"80"`**。该功能端到端仍是空操作，只是从"无 handler"变成了"有 handler 但必然拒绝"。

**附带语义问题**：即便把 `v_cruise` 传进去，`nRoadLimitSpeed` 在 `carrot_serv.py:1023/1133` 是 `min(v_cruise_kph, nRoadLimitSpeed, atc_desired)` 的**限速上限**，不是"定速微调"的目标值；调高它不会提高巡航设定速度。UI 写"定速微调"，语义也不匹配。需要先定契约：
- 若目标是**速度上限**：车机应发送 `arg=str(next)` 或 C3 读取 `v_cruise` 后写入 `nRoadLimitSpeed`；
- 若目标是**巡航设定增减**：应走 `v_cruise` 的独立通道（或模拟按键），不能复用 `nRoadLimitSpeed`。

### 2.2 M-24：签名配置会导致构建失败，且没有 release 产物（Major）

`AmapNavi-Reborn/app/build.gradle:9-15`：
```gradle
signingConfigs {
    release {
        storeFile file(RELEASE_STORE_FILE)
        storePassword RELEASE_STORE_PASSWORD
        keyAlias RELEASE_KEY_ALIAS
        keyPassword RELEASE_KEY_PASSWORD
    }
}
```
- `gradle.properties` 中**没有** `RELEASE_STORE_FILE/…`（实测无这些键），也未通过 `local.properties` 或环境变量注入。
- Groovy DSL 在**配置阶段**解析该块，未定义属性会抛 `Could not get unknown property 'RELEASE_STORE_FILE'` → **debug 构建同样失败**，不只是 release。
- 报告称"缺失时构建失败并给出明确提示"——这会把"没有密钥的普通开发者/CI"也挡在门外，属于回归。
- `app/build/outputs/apk/` 下仍只有 `debug/`，**没有任何 release 产物**，M-24 的闭环目标（产出标准 release APK）未完成。
- 另外：报告写"保留存量 `minifyEnabled true`"，但改动前该值是 `false`；本次实际把 R8 打开了。而当前 APK（mtime 10:35）早于 build.gradle 修改（11:08），**没有任何 APK 是在 `minifyEnabled=true` 下构建并验证过的**。`appcompat 1.2.0` 未降级，Dalvik `VerifyError` 风险仍未验证（见历次 B-02）。

**建议**：
```gradle
def hasReleaseSigning = project.hasProperty('RELEASE_STORE_FILE')
signingConfigs {
    if (hasReleaseSigning) {
        release {
            storeFile file(RELEASE_STORE_FILE)
            storePassword RELEASE_STORE_PASSWORD
            keyAlias RELEASE_KEY_ALIAS
            keyPassword RELEASE_KEY_PASSWORD
        }
    }
}
buildTypes {
    release {
        minifyEnabled true
        proguardFiles ...
        if (hasReleaseSigning) signingConfig signingConfigs.release
    }
}
```
并在无签名时使用 debug 签名以便本地构建；同时在真机 4.4 上验证 R8 产物。

4. 因此 **M-34 只能算"口径统一闭环"，不能算"内存安全闭环"**。30 号表写"已闭环（口径统一）"是准确的，但后续报告不应把它引申为"内存安全已论证"。

## 四、仍然存在、且本轮未触及的 Critical 回归（新 M-36）

`amap_navi.py:296-304`：
```python
ttc = min(ttc_list) if ttc_list else 0.0
```
`desire_helper.py:953-962`：
```python
rear_conflict = (behind_ttc <= 0.0) or (behind_ttc < ttc_threshold)
if rear_conflict:
    auto_lane_change_trigger = False
```
**机理**：`ttc_list` 只有在"后方存在正在接近（v < -0.1）的目标"时才非空。空车道、后车同速、后车远离、低速蠕行时 `ttc_list` 为空 → `0.0` → **所有变道被阻断**。
**结论**：这不是 fail-safe，而是把"无目标（安全）"与"传感器失效（未知）"合并成同一个哨兵，导致功能在绝大多数正常工况下不可用。
**修复**：必须引入"雷达在线 + 数据新鲜"的有效性位：
```python
lidar_alive = bool(self.shared_data.lidar_l or self.shared_data.lidar_r)
ttc = min(ttc_list) if ttc_list else (99.0 if lidar_alive else 0.0)
```
并在车机端/执行期保持 `(ttc <= 0) or (ttc < thr)` 的阻断语义。这样"无目标放行、失效阻断"两态才能同时成立——这也正是 31 号验收报告用例 2 与用例 3 无法在同一条提交上同时通过的根本原因。

> 建议在 30 号表中追加 **M-36（Critical，未修）**：无目标与失效不可区分导致空车道永久阻断。
