**结构性观察**：

1. **`carrot_man` 是单点宿主**：UDP 半打（6 个线程）+ Web 服务 + 命令分发 + 唯一的 `carrotMan` 发布者全在一个 `always_run` 进程里。任何一处未捕获异常打死主循环，`carrotMan` 就停止发布，而 `desire_helper` 会继续消费**最后一条**消息——**静默降级**，无告警。
2. **`DesireHelper` 跑在 `modeld` 里**（20 Hz，`DT_MDL=0.05`），不是 controlsd 的 100 Hz。这一点决定了"20 ms 接管""10 ms 内不阻塞主循环"等表述全部不成立（最坏 50 ms 一帧，再叠加锁存与执行器延迟）。
3. **三个 20 Hz 级别的"事实源"互不同步**：`carState`(100 Hz)、`carrotMan`(20 Hz)、`amapNavi`(20 Hz) 由三个独立进程/线程发布，`desire_helper` 每帧混合读取，**没有任何时间戳对齐或新鲜度校验**（`sm.alive` 只在个别分支用）。

## 二、库斯途专车适配性评估（核心）

### 2.1 CarParams 层：**没有任何一行是给库斯途的**

`opendbc/car/hyundai/interface.py` 中与乘用车动力学直接相关的赋值，全部是**平台通用值**，且全文件唯一的 per-car 分支是给 KIA Optima 的：

```python
# interface.py:189（全局）
ret.centerToFront = ret.wheelbase * 0.4
ret.steerActuatorDelay = 0.1
ret.steerLimitTimer = 0.4
...
ret.vEgoStarting = 0.1
ret.startAccel = 1.0                  # :202 全局
ret.longitudinalActuatorDelay = 0.5
ret.longitudinalTuning.kpBP = [0.]
ret.longitudinalTuning.kpV  = [1.]
ret.longitudinalTuning.kf   = 1.0
...
if candidate == CAR.KIA_OPTIMA_G4_FL:   # 全文唯一的车型专属覆盖
  ret.steerActuatorDelay = 0.2
```

**为什么这对库斯途不合适**：

| 参数 | 现状 | 库斯途的实际影响 |
| :--- | :--- | :--- |
| `centerToFront = wheelbase × 0.4` | 3.055 m → **1.222 m** 的硬性假设 | 该值直接进入横向 MPC：`factor1 = wheelbase − centerToFront`、`factor2 = (centerToFront·mass)/(wheelbase·tireStiffnessRear)`（`lateral_planner.py:41-42`）。前驱 MPV 的质心通常比轿车更靠前，而**满载 7 人时后轴载荷上升、质心后移**，同一常数无法同时适配空载/满载 |
| `mass`（来自车型表，未定位取值） | 单一常数 | 空载 1.69 t ↔ 满载 2.2 t，**±30%**。横向 `factor2` 与纵向加速度前馈都随质量线性缩放，单一常数意味着**要么空载偏软、要么满载偏硬**，且无法在中途感知载荷 |
| `startAccel = 1.0` | 全局常量 | 8AT 的 1-2 挡冲击与"请求加速度绝对值"关系不大，真正相关的是**请求的斜率（jerk）与变矩器锁止时刻**。把 `startAccel` 当"起步加速度上限"是语义误解（它是 `vEgoStarting` 阶段的基准值） |
| `longitudinalActuatorDelay = 0.5` | 全局 | 2.2 t 车重的制动/驱动响应确实更慢，但 0.5 s 是轿车级经验值；建议实测（见 §5 验证） |
| `steerActuatorDelay = 0.1` / `steerLimitTimer = 0.4` | 全局 | 长轴距车的 EPS 惯量更大，0.1 s 延迟可能偏乐观；`steerLimitTimer` 决定扭矩饱和后的等待，MPV 在低速大转角时更易触发 |

> **结论（可断言部分）**：不是"参数取错了"，而是**"没有为库斯途做任何标定动作"**。要做专车调优，第一件事是把 `wheelbase / centerToFront / mass / tireStiffnessRear` 这四个进 MPC 的量测准（空载与满载各一组），而不是先移植 NNFF。

### 2.2 NNFF 映射到 Palisade 的适用性风险

`substitute.toml:43` 已加 `"HYUNDAI_CUSTIN_1ST_GEN" = "HYUNDAI_PALISADE"`。方向合理（同为 2 t 级大车），但有两个必须验证的前提：

1. **数据可用性**：若数据集中不存在 `HYUNDAI_PALISADE` 的 NNFF 参数，`substitute` 会走回退路径并打日志——**必须在 C3 上确认启动日志无回退**，否则"已移植"只是文档事实。
2. **控制类型一致性**：NNFF 是**力矩控制**车型的前馈网络。若 `HYUNDAI_PALISADE` 在库中属 CAN-FD / 角控（`SteerControlType.angle`）车型，其训练样本的输入语义（方向盘角 vs 扭矩）与本车不同，直接 substitute 无物理意义。**需要核对 `values.py` 中该车型的 `SteerControlType` 与 `flags & CANFD`**。

### 2.3 横向平顺性：旋钮都在，但都没为 MPV 打开

```python
# lateral_planner.py:19-25
PATH_COST = 1.0
LATERAL_MOTION_COST = 0.11
LATERAL_ACCEL_COST = 0.0      # ← 横向加速度完全不惩罚
LATERAL_JERK_COST = 0.04      # ← jerk 惩罚极低
STEERING_RATE_COST = 700.0    # ← 转向速率惩罚很高（"很软"）
```

对 1.734 m 车高 + 后扭力梁的 MPV，这套权重组合的实际表现是：**转向变化慢（好事）但横向加速度与 jerk 不受约束（坏事）** —— 即"打得慢、但打起来之后照样甩"。后排晕车的直接诱因正是后者。

**建议**（不是全局改常量，而是**变道期动态加权**）：

```python
# 伪代码：仅在 laneChangeState != off 时提升 jerk/accel 权重
if cake:  # 仅示意
    LATERAL_ACCEL_COST_ACTIVE = 2.0
    LATERAL_JERK_COST_ACTIVE  = 0.20
```

理由：全局改会牺牲车道居中的抗扰能力（用户会感觉"跟不住线"），而变道期才是舒适性敏感区。

### 2.4 纵向：8AT 与 2.2 t 的三处不适配

```python
# carcontroller.py HyundaiJerk
jerk_u_min = 0.5
jerk_max_l = 5.0
...
self.jerk_l = min(max(1.0, -self.jerk * 2.0), jerk_max_l)   # 减速度 jerk 下限 1.0
self.cb_upper = np.clip(0.9 + accel * 0.2, 0, 1.2)
self.cb_lower = np.clip(0.8 + accel * 0.2, 0, 1.2)
```

| 问题 | 说明 | 建议 |
| :--- | :--- | :--- |
| `jerk_max_l = 5.0`、`jerk_l` 下限 `1.0` | 减速 jerk 允许到 5 m/s³、且下限不低 | MPV 满载建议 `jerk_l` 下限 0.6–0.8、上限 2.5–3.0；应做成 Params 可调，便于实测找点 |
| `jerk_u_min = 0.5` | 加速侧下限 0.5 已较保守 | 对 8AT 起步偏"绵"，但如果实测发现起步拖沓，是**它**而不是 `startAccel` 该调 |
| `create_acc_commands(..., soft_hold_mode)` + `self.soft_hold_mode = 2` | 固定值，无车型分支 | 库斯途有 AVH（`carstate.py` 的 `TCS15.AVH_LAMP`）。若 openpilot 的软驻车与 AVH 同时介入，可能出现"停稳后起步拔不出/互相顶"的现象。**必须实车验证，并按结果把 `soft_hold_mode` 做成可配** |

### 2.5 制动反馈缺失（对满载尤其关键）

```python
# carstate.py
# TODO: Find brake pressure
ret.brake = 0
```

库斯途 2.2 t 满载时的制动距离、热衰退、下长坡的制动力分配，都需要真实制动压力/减速度反馈。当前 `ret.brake` 恒 0，意味着：

- 纵向控制的"我的制动是否生效"只能靠加速度反推（有延迟）；
- 满载下坡时无法判断制动热负荷 → **安全裕度不可评估**。

**建议**：至少在 `carstate` 中用 `aEgo` 做制动生效的观测器（低通 + 死区），或从 ESP 报文取主缸压力（需查 `hyundai_k` DBC 是否含该信号）。

### 2.6 驾驶员接管时序：声明 20 ms，实际 80–150 ms

| 环节 | 耗时 | 证据 |
| :--- | :--- | :--- |
| `carstate.update_steering_pressed(abs(tq) > STEER_THRESHOLD, 5)` — **5 帧锁存** | ≈50 ms（card 100 Hz） | `carstate.py:217` |
| `DesireHelper.update()` 周期 | 50 ms（modeld 20 Hz，`DT_MDL=0.05`） | `desire_helper.py` 全文件用 `DT_MDL` |
| 状态机→`desire`→controlsd(100 Hz)→CAN(100 Hz) | 10–30 ms | 架构固有时延 |
| EPS 机械响应 | 30–60 ms | 硬件 |

**结论**：**最坏 ~190 ms，典型 ~100 ms**。文档中的"20 ms 无条件切断"是把 `DT_MDL` 误当成 0.02 的结果。
**建议**：(a) 接管判据改用**原始扭矩绝对值**（不经锁存），仅在"变道状态机"内使用；(b) 文档据实改为"≤150 ms"；(c) 若要真的快，应把变道抑制逻辑下移到 controlsd 的 100 Hz 循环（但这是较大改动，需评估与 `desire` 的耦合）。

### 2.7 三道门禁的实车有效性取决于三个 CAN 信号

| 门禁 | 依赖信号 | 若库斯途不上报的后果 | 验证方法 |
| :--- | :--- | :--- | :--- |
| 盲区（毫米波） | `ret.enableBsm = 0x58b in fingerprint[0]` → `carState.leftBlindspot/rightBlindspot` | `leftBlindspot` 恒 `False` → 车机 `LateralSafetyEvaluator` 第 2 道门禁**永久失效**（只剩激光雷达） | C3 上 `grep -c 0x58b` 指纹日志，或看 `carState` 报文 |
| 实线 | `carstate.leftLaneLine/rightLaneLine`（LKAS11 质量位） | `lane_line_info = 0` 恒 `< 20` → 视觉虚线判断退化为"只看车道存在" | 实车观察 `ShowDebugLog` 的 `carrot,left_blind` 与 `lane_line_info` |
| 停稳保持 | `TCS15.AVH_LAMP`（AVH 激活） + `soft_hold_mode` | 双重驻车 / 起步拔不出 | 红绿灯起停 10 次实测 |

> 这三项**代码里没有任何兜底或告警**：信号缺失时系统静默降级为"更宽松"的一侧。建议在 `carRotMan` 里上报 `featureAvailable` 位，车机 HUD 明确显示"BSD 不可用"。

## 六、验证方法（每类改动的验收标准）

| 改动类型 | 验收方法 |
| :--- | :--- |
| 安全门禁 | 六类反例注入：雷达断流 / 负距离 / 并排车 / 消息缺失 / 车机断电 / 畸形 param。要求"该阻断时阻断、该放行时放行"，脚本与原始输出入库 |
| CarParams 标定 | 台架：方向盘阶跃响应（记录上升时间/超调）→ 与模型预测对比；实车：同一弯道空载/满载各 5 次，比较横向误差 RMS |

## 七、给决策者的三句话

1. **现在最该做的不是"继续加功能"，而是"把已写的安全逻辑修对"**：一行哨兵 + 一处超时结算，就能让系统从"不可用且会骗人"变成"可用且可信"。
2. **库斯途的专车调优，缺的不是算法，是标定数据**：`centerToFront`、`mass`、`tireStiffnessRear`、`jerk` 四条实测曲线，比任何 NNFF 映射都更能决定手感。
3. **这套代码的可维护性尚可，但缺测试与可观测性**：一旦它要在 2 t 的 MPV 上长期跑，`carrotHealth` + 四个 pytest 模块的投入产出比远高于继续堆参数。
