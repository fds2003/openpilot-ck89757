## 一、统一方案总则与设计愿景

### 1.1 系统定位
本方案致力于构建一套**高度融合、各司其职、软硬件安全互锁的现代汽车车道级协同智驾领航系统**：
* **车机端（AmapNavi-Reborn）**：作为“中枢交互与宏观决策大脑”，运行于库斯途 960×1280 竖屏上，负责拦截高德车机版广播、渲染高精大字 HUD、解析车道拓扑并提供参数调优工作台；
* **C3 端（Comma 3 / openpilot cp-custo-amap）**：作为“微观感知与物理执行小脑”，运行于高通骁龙 845 芯片上，负责 1080p 视觉推理、微型激光雷达与原厂毫米波雷达融合、变道状态机仲裁及现代 C-CAN 总线 100Hz 底盘线控。

### 1.2 核心工程准则
1. **绝对真相准则 (Truth First)**：彻底摒弃一切未经源码验证的虚构代码与臆想参数，所有技术论据必须能回溯到文件物理路径与真实代码行号；
2. **功能安全准则 (Fail-Safe Priority)**：通信中断、传感器掉线或数据异常时，系统一律刚性偏向安全侧（阻断变道并平稳降级为单车道居中巡航），人类驾驶员拥有不可逾越的 20ms 绝对物理接管权；
3. **性能极限制约准则 (Resource Discipline)**：车机端坚持 Zero-Bitmap 纯矢量与流式零分配，严格把内存控制在 PSS 15.5MB，确保原厂倒车影像毫秒级瞬开。

## 二、整车软硬件全景真相裁决 (终结历史矛盾)

### 2.1 车机物理 RAM 2.0GB 唯一权威裁决与调度真相
根据《北京现代库斯途车机系统全景深度检测与分析报告_20261024.md》中 `/proc/meminfo` 的实测原始数据：
* **裁决结论**：**车机物理 RAM 为整整 2.0 GB (`MemTotal: 2,059,512 kB`)**；
* 历史文档中“1GB / 扣除显存后可用 350~400MB”系早期推测，与底层检测实测冲突，**自本总纲起正式作废**；
* **车机真实调度真相**：
-  - 航盛电子 D531MC 主板运行 Android 4.4.3 (API 19)，系统内固化常驻了数十个核心后台服务；
-  - 高德地图车机版（实车与测试手机统一安装版：`高德地图车机版8.5.0.600050悬浮(靓华修改).apk`，`com.autonavi.amapauto` v8.5.0.600050）自身导航时常驻占用高达 **`209 MB`**；
-  - 车机平时正常运转时，未被分配的绝对自由内存（`MemFree`）保持在 **约 150 MB 左右**（`Buffers: ~29MB`, `Cached: ~900MB`）。

---

### 2.2 伴侣应用常驻 PSS 15.5MB 的真正系统价值：保卫倒车影像生命线
* **旧推导纠偏**：在 2.0GB 总内存下，高德 209MB + 原版 250MB 虽不至于立刻将整个 2GB 内存撑爆，因此“459 > 350MB 必杀后台”推导作废；
* **新安全论证（Dalvik 堆与 R 挡时序）**：
  1. **Dalvik 单进程配额危机**：Android 4.4 对单个应用的 Java 堆配额极度紧缩。原版暴涨 250MB 主要是狂吃 Native 内存与碎片对象，导致 Dalvik 虚拟机高频触发 `GC_FOR_ALLOC` 全局挂起停顿（STW 达 80ms）；
  2. **R 挡倒车影像（`ViewMonitor.apk`）的 0.5 秒时序铁律**：驾驶员在中控按下电子换挡“R”按键的一瞬间，系统必须在 0.5 秒内完成全景摄像头 DMA 显存映射并推流上屏。如果伴侣应用在后台频繁高频分配大对象导致内存碎片化，倒车影像就会出现 **2~3 秒的卡顿甚至直接黑屏**；
  3. **结论**：将伴侣应用常驻内存压到 **`15.5 MB`**（仅占 2GB 总运存的 **0.7%**），完全不侵占 150MB 空闲自由内存，**彻底确保倒车影像毫秒级秒开，消除倒车盲区碰撞隐患**。

## 三、P0 阻断级缺陷根除与架构纠偏裁决

对既有审计报告指出的核心阻断项，实施不可逆的工程级裁决与根除方案：

### 3.1 纠偏一：torque_data 双重定义致命冲突裁决 (override vs substitute)
* **缺陷事实**：
  - `opendbc_repo/opendbc/car/torque_data/override.toml:77` 存在条目 `"HYUNDAI_CUSTIN_1ST_GEN" = [2.5, 2.5, 0.1]`；
  - `opendbc_repo/opendbc/car/torque_data/substitute.toml:43` 存在条目 `"HYUNDAI_CUSTIN_1ST_GEN" = "HYUNDAI_PALISADE"`；
  - `interfaces.py:79-80` 明确断言：`if sum([candidate in x for x in [sub, params, override]]) > 1: raise RuntimeError(...)`；
  - **严重后果**：openpilot 启动加载力矩参数时直接抛出 `RuntimeError` 崩溃！
* **裁决与方案**：
  **彻底删除 `override.toml:77` 的条目，独占保留 `substitute.toml:43` 的帕里斯帝 NNFF 模型映射**。单一所有权彻底消除重复定义冲突，确保 openpilot 平稳开机！

---

### 3.2 纠偏二：后车时距 (TTC) 语义反转与空车道误阻断根除方案
* **缺陷事实**：此前代码在无后车逼近目标时输出哨兵 `ttc = 0.0`，导致消费端 `(behind_ttc <= 0.0)` 恒为真，空车道所有变道被永久误阻断；
* **裁决与方案**：**实行“道路净空”与“传感器离线”的三态解耦**：
  $$\text{TTC} = \begin{cases} 
  99.0\text{ s}, & \text{后向传感器正常在线，且净空无逼近目标 (允许变道)} \\
  \min(\text{TTC}_{approaching}), & \text{检测到后车快速逼近 (若 } < \text{门限则刚性阻断)} \\
  0.0\text{ s}, & \text{传感器彻底离线/通信超时/数据损坏 (Fail-Safe 刚性阻断)}
  \end{cases}$$
  消费端判定公式冻结为：`rear_conflict = (behind_ttc <= 0.0) or (0.0 < behind_ttc < ttc_threshold)`。彻底消灭空车道误杀！

---

### 3.3 纠偏三：车机上行指令 (CANCEL / SPEED_LIMIT) 消费全链路闭环
* **裁决与方案**：
  1. **变道紧急撤销 (`CANCEL`)**：在 `desire_helper.py` 中建立对 `carrotCmd == "CANCEL"` 的显式消费分支，在 **50ms 内立即将变道状态机重置为 `off`，清空变道计数，回拉原车道并播报“领航已退出”**；
  2. **巡航控速与电子眼减速 (`SPEED_LIMIT`)**：在 `carrot_serv.py` 的 `command_handlers` 字典中注册 `"SPEED_LIMIT"`，带 `0 ≤ v ≤ 160` 安全白名单校验，让车机微调与匝道减速真正起效。

---

### 3.4 纠偏四：变道状态反馈 (atc_state) 实时下发与虚假成功终结
* **裁决与方案**：
  1. C3 在 `make_navi_message()` 中通过 `"atc_state"` 实时下发当前底层变道状态（0:待机, 1:预备, 2:执行, 3:完成）；
  2. 车机端 `OvertakeStateMachine.kt` 在超时未收到状态 3 时，**严格执行撤销、报警并锁定长冷却，彻底废除“超时即当完成结算”的掩耳盗铃逻辑**。

## 五、双端车载局域网通信契约全景规格字典

### 5.1 端口绝对交叉咬合矩阵 (7705 / 7706 / 4210 / 5510)
双端端口必须严格交叉对齐，绝不产生“同向冲突”：

| 通信通道 | 传输协议 | 监听方 (bind) | 发送方 (sendto) | 报文职责与说明 |
| :---: | :---: | :---: | :---: | :--- |
| **设备发现探针** | UDP 广播 | C3: `4210` | 车机: `255.255.255.255:4210` | 车机发送 `discover` 探针，C3 锁定车机 IP。 |
| **设备握手应答** | UDP 单播 | 车机: `5510` | C3: `车机IP:5510` | C3 回送 `c3_pong` 及自身真实分配的 IP。 |
| **感知遥测下行** | UDP 单播 | **车机: `7706`** | **C3: `车机IP:7706`** | C3 每 50ms（20Hz）推送 81 项高精感知遥测。 |
| **控制指令上行** | UDP 单播 | **C3: `7705`** | **车机: `C3_IP:7705`** | 车机即时下发超车、撤销与定速指令。 |

---

### 5.2 免配置探针自动握手、动态 IP 学习与反弹防护
* **探针载荷**：车机广播 `{"cmd":"discover","port":5510}` 及 `c3_ping` 字节串；
* **C3 应答载荷**：
  ```json
  {
    "resp": "c3_pong",
    "device": "comma3",
    "status": "ready",
    "device_id": "c3",
    "auth": true,
    "ip": "192.168.3.243",
    "version": "openpilot-cp-custo"
  }
  ```
* **反弹防护**：C3 回包精准探测自身接口 IP，车机端优先采信底层 UDP 物理源地址（`packet.address.hostAddress`），双重保险彻底消灭“车机把指令发给自身”的静默故障。

---

### 5.3 81项高频遥测下行规格 (20Hz Ratekeeper)
C3 以每 50ms 一帧向车机端推流，核心字段格式标准：
```json
{
  "active": true,
  "v_ego": 31.94,
  "v_ego_kph": 115.0,
  "v_cruise_kph": 120,
  "steer_angle": -1.2,
  "gas_press": false,
  "brake_press": false,
  "engaged": true,
  "lead1": true,
  "drel": 58.5,
  "vrel": -0.8,
  "left_blindspot": false,
  "right_blindspot": false,
  "lidar_behind_vdist_time": 99.0,
  "lb_drel": 42.0,
  "rb_drel": 48.0,
  "atc_state": 0
}
```
* **量纲铁律**：`lb_drel` 与 `rb_drel` 在 C3 发送端统一取绝对值换算为**正米制浮点数（如 42.0）**，车机端 `parseDistanceMeter` 采用 200m 阈值防重除，彻底杜绝 0.042m 贴身误判。

---

### 5.4 上行控制指令规格 (单调防重放、10s 超时自愈)
```json
{
  "cmd": "OVERTAKE",
  "arg": "LEFT",
  "direction": "LEFT",
  "param": 1,
  "seq": 1024,
  "index": 1024,
  "v_cruise": 120,
  "blinker": 1,
  "timestamp": 1730592000000
}
```
* **防重放机制**：C3 维护 `cmd_index`，仅当 `seq > cmd_index` 时放行指令；
* **重启自愈机制**：若超过 10.0 秒未收到任何指令，C3 自动将 `cmd_index` 重置为 `-1`，确保车机 App 重启后序号从 1 开始不再会被无情抛弃。
