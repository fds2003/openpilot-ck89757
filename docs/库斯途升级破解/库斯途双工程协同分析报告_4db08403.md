## 0. 结论速览

### 0.1 一句话总结

这两个工程各自都有"能跑"的实现，但**拼在一起时协同语义是矛盾的**：对同一个"侧后方有无来车"的判断，车机端把「无数据」解释成**安全**，C3 端把「无数据」解释成**危险并永久阻断**；车机端把「4.5 s 超时」解释成**变道成功**，C3 端此时根本没执行变道；车机端下发的巡航/限速指令在 C3 端**没有任何消费者**；而 C3 端为打通链路加的 `amapNavi` 消息老化判据，因为频率被写成 `0` 而**恒为真**。结果是：在默认（无 BSD 外设）配置下，"自主超车"这条链路**永久空转**——车机每隔约 20 s 重试一次、每次提示"变道完成"，而方向盘从未被授权执行；同时 C3 每 2 s 播报一次"后方来车"。这不是调参问题，是**契约与状态语义问题**，必须两端一起改。

### 0.3 架构层判断（最重要的一条）

**用一条消费级 Wi-Fi UDP 链路去承载"变道安全仲裁"，是这套设计里最根本的问题。** 端 B 是 2012 年的 i.MX6 + Android 4.4 + Dalvik + 无功能安全等级的娱乐主机，却在承担：实线判定、侧后方净空判定、驾驶员干预判定；而端 A 有一台带摄像头/GL 网络/激光雷达外设、运行 100 Hz 控制环、直连 panda 的设备。当前实现把**决策权**放在弱端、把**执行权**放在强端，弱端一丢包就"按成功处理"。§7 给出职责重划方案。

## 3. 十一项跨工程缺陷详解（J-1 ~ J-11，按严重度排序）

### J-1 【P0】"无数据"的语义在两端相反，导致自主超车永久空转 + 双套矛盾语音

**机制**（把两端合起来才看得清）：

```
                    C3（_data_deal_thread → public_amap_navi）        车机（parse → LateralSafetyEvaluator）
无 BSD 外设/无后向目标   main_lb_drel=None → ttc=0.0                      msg.pop("lb_drel") → parser 默认 −999999
                        → rear_conflict = (0.0<=0.0) = True → 阻断         → parseDistanceMeter → 999.0 m → "净空充足" → 放行
后车正以 40 km/h 逼近    d 有值、v<-0.1 → ttc=… 若 < 档位阈值 → 阻断        d 有值、距离 < max(10, v_ego·2.0) → 阻断
后车同速/远离           v 不满足 < −0.1 → 不追加 → ttc=0.0 → 阻断 ⚠️        距离足够 → 放行 ⚠️
```

**后果（这是本文档最重要的单条结论）**：在**最普通的场景**（后方无车、或后车与自车同速）下：

1. 车机的 4 层门禁（`navValid/isHighway` → 前车压速 → 地图车道 → BSD/距离）全部通过 → 下发 `LANECHANGE`；
2. C3 的 TTC 门禁因 `ttc = 0.0` 阻断，但**仍然每 2 s 调用 `lane_change_audio(True, 6, 0)`（"后方来车"）** —— 而这个门禁位于 `update()` 主干，**与是否有变道请求无关**，等于正常巡航时也每 2 s 播一次警；
3. 车机进入 `EXECUTING` 等待 `atc_state == 3`，永远等不到；
4. 4.5 s 后车机 `handleExecuting` 超时分支把状态写成 `FINISHING` → **播放 `LANE_CHANGE_OK`（"变道完成"）** → 20 s 冷却 → 回到 IDLE → 条件依旧满足 → **再来一轮**。

于是：**车机喇叭每 ~25 s 播"变道完成"，C3 每 2 s 播"后方来车"，方向盘从未动过。** 驾驶员面对两套互相矛盾的语音，最可能的处置是关掉功能或忽视告警——这比没有该功能更危险。

**修复要点**（必须双端同改）：见 §7.1 的 `ttcStatus` 三值化 + §7.3 的 `laneChangeStatus` 回执通道；同时 C3 端把警语音与"确有请求"绑定。

### J-2 【P0】协议里没有"被拒绝"这一状态，车机的成功判定只能靠猜

C3 端唯一可用的失败线索是 `msg['op_blocked']` / `msg['road_blocked']`（`amap_navi.py:1854-1855`，由 `atc_type` 推导），以及 `atc_state`；车机**两个都没解析**（`CarrotTelemetryParser.kt:16-45` 的 25 键清单里没有 `op_blocked`/`sound`/`atc_type`）。

**这是"两端各自都不完整、合起来才暴露"的典型**：
- 端 A 报告（单看 C3）能看出"0.0 哨兵会被误解释"；
- 端 B 报告（单看车机）能看出"超时当作完成"；
- **只有把两端合起来才能看出：超时当作完成，是因为协议里根本没有别的可选路径。** 车机端代码作者写的 4 个单测（`OvertakeStateMachineTest.kt:136`）用人为制造陈旧时间戳来"通过"看门狗测试，恰好掩盖了这个通道缺失。

**修复**：新增 `laneChangeStatus: uint8`（`0=IDLE, 1=PRE, 2=EXEC, 3=DONE, 4=REJ_TTC, 5=REJ_LINE, 6=REJ_BSD, 7=REJ_STATE, 8=ABORT_DRV`）+ `laneChangeReqId`（回显请求 id）。车机端把状态机的 `EXECUTING` 收敛条件改为**显式 DONE/REJ/ABORT**，任何超时一律降级为 `REJ_TIMEOUT` 并触发惩罚冷却 + "变道未执行"语音，绝不许播 `LANE_CHANGE_OK`。

### J-4 【P1】"三级超车风格"只在一端生效，两端安全模型数学上不同、且互不校验

|---|---|---|
| 判据 | 后向 **TTC** = `abs(drel_mm)/1000 / abs(vrel)`，阈值 `{0:1.8, 1:2.5, 2:3.5}` s | **距离** ≥ `max(10 m, v_ego(m/s) × 2.0 s)`，**与档位无关** |

**修复**：把"侧后安全"定义为**一个**函数，用同一份参数（建议以 TTC 为主 + 绝对距离下限 + 车长修正），在两端各自执行同一实现，并把参数随握手包一次性下发/校验（`paramHash`），任何一端参数不一致就禁用自动变道并提示。

### J-5 【P1】"目标车道是否可用/是否实线"两端来源不同，取交集后成功率被系统性压低

* 车机：`RouteLaneMarkingOracle.isTargetSolid()` 只看高德 `EXTRA_DRIVE_WAY` 的目标车道首字符是否为 `'X'`；`LaneWayParser` **只认 `|` 分隔**，而自家 `docs/AMAP_BROADCAST_SPEC.md:40` 的示例是 `s/s/s/x/r`（`/` 分隔、小写 `x`）。若高德实发 `/` → `tokens.size==1`、`targetLaneIndex()` 恒 −1 → 车机侧永远 `NO_TARGET_LANE`；若实发小写 `x` → **禁行车道被当成可跨越虚线（fail-open）**。
* C3：`lane_change_available = (lane_available or edge_available) and lane_line_info < 20`（`desire_helper.py:747`，视觉线型 + 车道宽度稳定计数 `> 0.2 s`）→ 完全另一套判据，且不看地图。

**两端交集** = 「地图说可变道」**且**「视觉说虚线且宽度稳定」**且**「盲区干净」**且**「TTC 达标」**且**「App 的 2 s×v 距离达标」**且**「不在 0.2 s 请求窗内被其他门拒掉」**。任一端过严/过松都会表现成"按钮点了没反应"，而两端都没有归因通道（J-2）。

**修复**：车道合法性以**车载视觉/C3 为唯一权威**（端 A 已有 `laneLines`/`lane_width` 且车机根本没读）；车机侧只保留"目标车道在地图上不可用"这一条**阻断**语义（保守否决权），不再有独立放行权。

| C3 先收到 `SPEED_LIMIT` 再收到 `LANECHANGE`（同 index 空间，`cmd` 覆盖） | **`remote_cmd` 被后包覆盖，变道请求丢失**（无队列，共享变量单槽） |
| 车机 App 重启（seq 归 1） | C3 的 `cmd_index` 仍是旧大值 → 需空等 >10 s 才允许复位（`last_cmd_time` 判定）→ **这 10 s 内所有指令被丢** |
| 车机内部 `+=100` 与头单元 `1..N` 交叉 | 序号语义不单调 → 合法命令被丢弃 / 复位逻辑被反复触发（`cmd_index == -1` 分支） |

**修复**：每条指令带 `reqId`，C3 端改为 **`List(Command)` 消息字段**（capnp 已可表达），按 `reqId` 去重与有序消费；C3 内部 DISPLAY 之类的自发命令用另一条 `source` 字段区分，**不与外部序号共用计数器**。撤销必须 3 发（间隔 100 ms）并要求回执（J-2）。

### J-10 【P1】同机端口角色反转与自环（把两个进程内嵌后暴露）

`amap_navi` 被内嵌进 `carrot_man` 进程后，本机同时：
* `bind :4210`（响应发现）、`:4211`（外设）、`:4212/4213`（车道/回显）、`:7705`（车机指令）；
* `bind :7706`（carrot_man 收手机 App）、`sendto :7705`（carrot_man 广播给手机 App）、`sendto :7706`（amap 发遥测给车机）。

其中 **`carrot_man.py:433` 的广播 `sendto(255.255.255.255, 7705)` 会被本机 `amap_navi.py:648` 的 `bind :7705` 收到**（本机自己发的子网广播会回环给自己），于是**每秒 10 次把自家 JSON 灌进车机指令解析器 `_process_single_packet`**：`json.loads` 白跑，并且**这条伪造通道没有 `app_ip` 校验**（`_update_blinker/_update_control/_update_sensors` 三个函数都不校验来源）。此外 `carrot_man_thread` 收到自己广播的回环包后会把自己 IP 设成 `remote_addr`（`carrot_man.py:641-643`），干扰"远端已连接"的判定。

`_discovery_responder_thread` 还把本机出接口 IP 通过 `connect((ip,80))` 探测（`:620-626`），在车机侧 `UdpDeviceDiscovery:87` 又存在 `localSocket.send(pingBytes, probeTarget, localPort)`（**向自己的 5510 发探针**）→ 双端各留了一个自问自答路径。

**修复**：① 立刻把车机指令通道换到独立端口（如 7707）并**统一端口常量表**；② `_process_single_packet` 全量入口校验来源 IP；③ `carrot_man.py:433` 与 `amap_navi.py:1631-1634` 加 `if ip == local_ip: continue`；④ 车机停止 `localSocket.send(..., localPort)`；⑤ 恢复 `amap_navi` 为独立进程（消除自环，也让资源隔离/看门狗有意义）。

### J-11 【P1·安全】把两端串起来看，这是一条从 Wi-Fi 直达方向盘的通路

```
① 伪造/中间人：同一 Wi-Fi（README 推荐"手机热点"，即开放子网）
   → 向 C3:7705 发 {"cmd":"LANECHANGE","direction":"LEFT","index":<大值>}
   → _update_command 无鉴权；_update_sensors 的盲区字段可任意写（无来源校验）
   → desire_helper 触发变道（若 TTC/视觉条件凑巧满足）
② RCE：C3 UDP 4213 / ZMQ 7710 的 echo_cmd → subprocess(shell=True)
   → 可改写 /dev/shm/params（DisableDM、转向标定）→ 或直接 rm -rf
③ 车机侧同样无鉴权：伪造 6 个键（engaged/v_ego_kph/v_cruise_kph/lead1/drel/vlead）
   → 车机状态机自行判定"可超车"并向 C3 请求；`UdpDeviceDiscovery.kt:126`
     的 `if (resp!="c3_pong" && status!="ready" && device!="comma3") return null`
     —— **三个条件用 && 连接**（应为 ||）：任一根字段命中即被认定为合法 C3
     → 攻击者可抢占 targetAddress；`auth` 字段 optBoolean 默认 **true**（缺字段=通过）
④ C3 端点 4 后，横向已无硬件兜底（safety `//tx=false`、max_steer 512，见端 A 报告 §5.1）
```

**结论**：这条链路上"最弱的一环"是**协议无鉴权**，而不是任何一端的实现细节。任何"这套系统只在我车里、局域网不连外网"的说法都不成立——车辆自身的 Wi-Fi（航盛热点/手机热点）日常被乘客设备接入。**必须**：绑定预共享密钥 + HMAC 截断位、`||` 逻辑修正、必需键校验、来源 IP/MAC 白名单、删除 `echo_cmd`、车机 Activity 全部 `exported="false"`、`allowBackup="false"`（车机侧 5 个 `exported=true` + `VIEW` 过滤器，任意第三方 App 可拉起设置/设备页干扰目标 IP）。

## 4. 端到端时序预算

### 4.1 单跳延迟（全部取自代码里的真实频率/分频常数）

| 跳 | 载体 | 代码依据 | 节拍 | 最坏等待 |
|---|---|---|---|---|
| 1 | C3 → 车机 遥测推送 | `amap_navi.py:1585` `Ratekeeper(10)`（**不是文档说的 20 Hz**） | 10 Hz | **100 ms** |
| 2 | 车机感知 → 决策 | `RelayEngine.kt:214-220`：`tick()` **只在收到遥测包时**执行（无独立定时器，见 §1.2-S1） | 跟随跳 1 | +0（但断流时永不执行） |
| 3 | 车机 → C3 UDP | `CarrotUdpClient.kt:124-131` `scope.launch(Dispatchers.IO)` | 即时 | 1–30 ms（热点抖动更差） |
| 4 | C3 命令接收 → `SharedData` | `amap_navi.py:643-657`（阻塞 recv，事件驱动） | 即时 | ~1 ms |
| 5 | `SharedData` → `carrotMan` capnp | `carrot_man.py:399` `Ratekeeper(10)` 的广播循环里 `get_data_amap_navi()` + `update_navi()` 发送（`carrot_serv.py:1547`） | 10 Hz | **100 ms** |
| 6 | `carrotMan` → `DesireHelper`（在 modeld） | `modeld.py:474`，`DT_MDL = 0.05` | 20 Hz | **50 ms** |
| 7 | `desire` → `lateralPlan` (plannerd) | `plannerd.py` 以 modelV2 触发 | 20 Hz | **50 ms** |
| 8 | `lateralPlan` → `controlsd` | `DT_CTRL = 0.01` | 100 Hz | 10 ms |
| 9 | `controlsd` → `carcontroller` → CAN | `carcontroller.py:310` LKAS11 `frame % 2` | 50 Hz | 20 ms |

### 4.2 关键路径合计

| 路径 | 最坏 | 典型 | 文档/README 宣称 | 判定 |
|---|---|---|---|---|
| **车机 CANCEL → 方向盘停止施加变道扭矩** | **≈ 260–330 ms** | ≈ 150–220 ms | "50 ms 内立即中止变道" | ❌ 差 **5–6 倍**；50 ms 只够跳 1→跳 3 的网络往返 |
| **驾驶员反抗打盘 → 变道退出**（不经过车机） | ≈ 80 ms | ≈ 40 ms | "50 ms 内瞬间注销" | ✅ **这条基本成立**（`desire_helper.py:1350` 在 modeld 内直接判 `steeringPressed`，20 Hz；README 把两条路径混为一谈） |
| 车机 → C3 → 真正发起变道（端到端请求延迟） | ≈ 250–330 ms | ≈ 150–200 ms | "毫秒级" | ❌ |
| **而 C3 给这条请求的执行窗口只有 0.2 s** | `desire_helper.py:508` `int(0.2/DT_MDL)`=4 帧 | — | — | ⚠️ **请求在传输里就可能过期**：只要跳 5/6 抖动一次（10 Hz→20 Hz 各一跳），200 ms 窗内条件没凑齐，`carrot_lane_change_count` 归零，请求**静默作废**，车机侧完全不知道 |

### 4.3 由此导出的两个结构性结论

1. **"请求窗 0.2 s" 与 "链路往返 0.15–0.33 s" 是矛盾的。** 一个跨越 6 个异步节拍的命令通道，被上游用一个只有 4 帧生命周期的标志位消费；抖动一次即丢。**必须改为"命令 + 有效期 + 回执"的语义**（跳 5 之后由 C3 明确回应 ACCEPTED / 原因），否则"点击无反应"会成为该功能的常态表现。
2. **端到端时延里最不可接受的其实不是 CANCEL（260 ms 在物理上还够），而是跳 1 的 10 Hz + "只在收到包时 tick"**：真实高速上 100 km/h 时 100 ms = 2.8 m 位移，`lb_drel`/盲区标志都是 100 ms 前的世界。对**车长 4.95 m** 的库斯途，"后车相对我车尾的位置"每 100 ms 变化可达 1.5–2.5 m（80 km/h 逼近差速场景），意味着车机 `minStaticClearanceM=10` 这类 1 m 级判据在 10 Hz 下已接近分辨率极限。**下行必须 ≥25 Hz 且车机需要独立节拍源（60 Hz 定时器 + 时间戳老化）**。

### 4.4 时延预算重设计（建议写进协议 doc）

```
端到端目标（请求 → 方向盘开始执行）：≤ 120 ms 95 分位
  跳1 下行遥测           25 Hz (40 ms)   + 单调时间戳 + 老化(≤ 80 ms)
  跳2 车机决策           独立 50 ms 定时器驱动（不再依赖收包）
  跳5 C3 内部            车机命令改为直发 amapNavi capnp（去掉 10 Hz 搬运跳）
  执行窗                 从 0.2 s 提升到"命令带 reqId + 1.5 s TTL + 回执"
预算分解：网络 10 + 车机决策 20 + capnp 一跳 40 + modeld 40(planner 50Hz) + 控制 20 ≈ 130 ms
```
（把 `carrot_man` 的 10 Hz 搬运跳去掉，是收益最大的一刀——见 §7.4。）

### 5.1 合并视图：为什么"两端各自的安全措施"合起来等于没有

| 防线 | 端 A 现状 | 端 B 现状 | 合并效果 |
|---|---|---|---|
| 硬件（panda）横向限幅 | `//tx=false` 注释掉、`max_steer=512` | 无感知 | **最后一道线没了** |

| 远程运维 | `echo_cmd` RCE ×2、8088 无鉴权写参数、FTP 明文凭据自动上传、`git pull` 热更 | 5 个 `exported=true` Activity、`allowBackup=true`、日志写全局 `/sdcard/logs/` | **两端互为攻击跳板**：拿下 Android 4.4 车机（永不打补丁）→ 内网直连 C3 的 RCE 面 |

### 5.2 攻击路径实例（可按此做验证）

### 5.4 隐私与合规（合并视角新增的暴露面）

## 6. 库斯途 MPV 特性在两端的缺失

端 A 报告（§3）讲的是 CAN 侧的 CarSpecs/EPS；这里只列**由车物理特性决定、但被放在端 B（Android/地图侧）或用参数形式表达**的问题——这类问题单看任意一个工程都会漏。

### 6.1 车长 4.95 m / 轴距 3.055 m：变道"完成"的判据在两端都不成立

* 端 B 的完成判据只有 `atc_state == 3` 或 4.5 s 超时。而 MPV 完全占用新车道（车身全部 entered new lane）在 100 km/h 下一般需要 5–8 s，端 B 的 `executeTimeoutMs = 4500` **短于物理完成时间** → 正常变道也会先超时；叠加 J-5 又会让超时被当成成功。
* 端 B 完全**没用**端 A 已提供的 `l_edge_dist`/`distanceToRoadEdge*`、`lane_width`、视觉车道线概率 → 本可以直接判"车身是否已完全进入新车道"（用路沿距离差 + 航向角），却选择了一个不可靠的魔数。

### 6.2 满载 2.3 t + 高重心 + 后扭力梁：端 B 的制动/净空模型按空车轿车标定

| 端 B 参数 | 现值 | 问题 |
|---|---|---|
| `minStaticClearanceM` | 10 m（硬编码） | 库斯途车长 4.95 m：后车 10 m ≈ 1.05 个自车距；满载 2.3 t 时 100→0 km/h 制动距离轻松 45–55 m，**"让后车被迫急刹"的净空标准形同没有** |
| `minSafeTimeHeadway` | 2.0 s（硬编码，且用**自车速度**而非接近速度） | 后车 80 km/h 逼近而自车 100 km/h 时真实 TTC = 相对速度决定；当前模型判"远"，但一旦变道完成、后车需要在 <2 s 内重建立距离，对高重心+空承载轮胎是急刹工况 |
| `RampSpeedPlanner` | 目标 60 km/h、`a = 1.0 m/s²`（且参数不生效，J-6） | 满载 MPV 进 60 km/h 匝道的舒适/安全减速率应实测（通常 0.8–1.2 m/s² 且受 tire/ESC 干预影响），1.0 属未验证常数 |
| `driverSteerThresholdDeg` | 25° 角差 | 用**绝对方向盘角差**判"驾驶员反向打轮"：库斯途 `steerRatio=17` 且变道本身在打方向盘（`steerAtExecutionStart` 取下发瞬间值，若那一瞬正在弯道修正则起点即误差），高速弯道中 25° 完全可能被 openpilot 自己的转向动作达成 → **误判驾驶员干预 → 撤销 + 60 s 冷禁**（`interruptCooldownMs=60000` 硬编码） |
| `prepareBlinkMs` | 1.2 s | 4.95 m 车身，后车用 1.2 s 观察到灯并作出反应刚好在临界；MPV 建议 ≥2.0 s，并要求预闪期内二次 BSD 静默 |
| `minEngageSpeedKmh` | 60 km/h 无滞回 | 满载高速爬坡时常速在 55–65 抖动 → 状态机每帧在 IDLE/EVALUATING 之间来回（`OvertakeStateMachine.kt:107,133` 无迟滞），并可能反复重置 `stateSinceMs`，让计时永远达不到 4.5 s，**看起来"卡在超车评估"且无提示** |

**建议**：把这些量做成**车型参数块**（随握手从端 A 拉取或由配置生成），而不是 Kotlin 默认值：

```kotlin
data class VehicleProfile(                       // ← 库斯途专属，取代散落的硬编码
    val lengthM: Float, val wheelbaseM: Float, val massMinKg: Int, val massMaxKg: Int,
    val steerRatio: Float, val maxComfortLatAccG: Float,   // 0.18~0.22（MPV，非 0.35 轿车）
    val laneChangeMinTimeS: Float,                          // 5.0~8.0，随车速
    val brakeDecelFullKg: Float,                            // 满载实测，用于净空推导
)
```
端 A 已经在 `CarSpecs(mass=1690, wheelbase=3.055, steerRatio=17)` 里有一份（且数值本身待实车核实），**两端各有一份车型参数、彼此不同步**，这本身就是缺陷。

### 6.3 地图数据 vs 车载视觉：谁有权说"这里可以变道"

端 B 把"实线/禁行"完全押在高德的 `EXTRA_DRIVE_WAY` 上：
* 分隔符/大小写与自家文档冲突（J-8 的 `|` vs `/`、`X` vs `x`）→ 一侧失效或一侧 fail-open；
* 高德车道引导只在**接近路口/分岔**的路段下发，且巡航/导航态与字段集合不同（`KEY_TYPE` 未被区分，`docs/AMAP_BROADCAST_SPEC.md` 定义的 `CUR_SPEED/CUR_ROAD_NAME/ROUTE_REMAIN_*` 代码一个都没读）；
* 高速上"最左侧超车道 + 实线区间 + 隧道限速"这类真正需要阻断的场景，恰恰是地图车道信息最容易缺失/滞后的地方（`road_blocked` 字段端 A 会发 "隧道" 判断，端 B 却**不解析**）。

**结论**：车道标线合法性必须以**端 A 的视觉车道线**为唯一权威；端 B 的地图只提供"目标车道是否存在、是否推荐"这类**辅助否决**信息，禁止提供"可以压线"的许可。

### 6.4 端 A 报告结论在合并视角下的"传染效应"

端 A 报告（`openpilot-ck89757-库斯途代码深度分析报告.md`）里那 6 条（`mass=1690` 台版 / `steerRatio=17` learner 猜 / `centerToFront=0.4×L` / `STEER_MAX=409` 未实测 / 8AT `startAccel=1.0` 为阶跃而非文档所称抛物线 / `minEnableSpeed` 未用 / HOD 未解析 / 盲区框常量按轿车 / panda `tx=false`）不是"另一份报告的事"：
* `steerRatio` 与 EPS 角度↔力矩关系错 ⇒ 端 B 用 `steer_angle`（度）判"驾驶员反向打轮"的 25° 阈值失去物理意义（同一 25° 在真实车上的横向含义未知）；
* panda 横向兜底被注释 ⇒ 端 B 的任何误判（J-1/J-2/B-S3 超时误成功）**不再有第二道闸**；
* `loggerd` 停用 + `carrot` 无 cloudlog ⇒ 端 B 的"变道完成"假播报在事后无法归因（两端都没有可回放的证据链）。

## 7. 联合修复方案（含协议 v2 提案）

### 7.1 先立"契约单一事实源"（不做这条，其余修复都会再次漂移）

```
custo-proto/                       ← 新建小型共享仓库（或作为两端共同 submodule）
  ├─ schema.toml        唯一的键名/类型/单位/有效域/缺省语义定义（含 v2 新增的 ttcStatus、laneChangeStatus、reqId）
  ├─ consts.py / Consts.kt          由 schema 生成（Python + Kotlin 双出码）
  ├─ golden/uplink_*.json           真实抓包样本，两端各自跑一致性测试
  └─ version                        proto=2，握手时交换，不一致即禁用协同功能
```

**出码 + 一致性测试是硬要求**：本次发现的 8 处字段级不一致（`v_ego`/`v_cruise`/`left_line_type`/`blinker` 类型/`OVERTAKE`/`SPEED_LIMIT`/`driver_steering`/`lb_drel` 单位）**全部属于"有一处对不上就静默失效"的类型**，靠人眼比对注释（端 B 的 `// M-13:`）不可能防住。

### 7.2 三值有效性：一个改动同时解决 J-1 / J-2 / S2(fail-open)

```toml
# schema.toml
[rear.threat]        ttcStatus = "enum{UNKNOWN=0, NO_THREAT=1, THREAT=2}"   # 不再用 0.0 复用两义
                     ttcS      = "float32, 仅当 THREAT 有效"
[rear.geometry]      lbDrelM   = "float32, 单位米, >=0 表示目标存在, 无效=字段缺省即 UNKNOWN"
                     vrelMps   = "float32, 正=逼近"        # 端 A/B 统一符号约定并写进文档
[ack]                laneChangeStatus = "enum{...REJ_TTC, REJ_LINE, REJ_BSD, REJ_STATE, ABORT_DRV, DONE}"
                     reqId = "uint16"
```
端 A 消费逻辑改写：
```python
if navi.ttcStatus == UNKNOWN:  → 沿用原厂 BSD/视觉（若都无 → 禁止"自动"变道，但**允许驾驶员打灯变道**）
if navi.ttcStatus == NO_THREAT: → 放行
if navi.ttcStatus == THREAT and navi.ttc < thr[mode]: → 阻断（仅在确有请求时播报）
```
**关键取舍**：UNKNOWN 不应该同时禁掉"驾驶员请求"。当前实现（`desire_helper.py:1247-1259`）把人工打灯变道也一起打死，等于"没装 BSD 外设的用户不能变道"——这是功能设计缺陷，不是安全冗余。

### 7.3 命令通道：从"共享变量 + 10 Hz 搬运"改为"capnp 队列 + 回执"

```
现状：UDP → SharedData（单槽 remote_cmd） → carrot_man 10Hz 搬运 → carrotMan → modeld 20Hz
改为：UDP → AmapNaviServ 直接 pub `amapCommand`（capnp，List<Command{reqId,cmd,arg,ttlMs}>）
      modeld 端 DesireHelper 按 reqId 去重消费，执行结果经 `amapAck` 回到端 B
收益：去掉一整个 100 ms 跳；消除"后一条覆盖前一条"（J-9）；消除 SharedData 无锁共享（端 A 报告 §6.5）
```
同时端 B 的状态机改成**回执驱动**：`EXECUTING` 只有在收到 `DONE` 才进 `FINISHING`；`REJ_*` → 提示原因 + 短冷却；无任何回执 → `TIMEOUT→FAILED`（**绝不播成功音**）。撤销 3 连发 + ACK 校验。

### 7.4 权威重划（最重要的一条架构决策）

| 判定 | 应由谁做 | 理由 | 需要移除/降级 |
|---|---|---|---|
| 车道合法性（实线/导流线/隧道）| **端 A（视觉）** | 车规传感器、100 Hz、与执行同进程 | 端 B 的 `isTargetSolid` 只保留"否决权"（不可由地图给绿灯） |
| 侧后净空 | **端 A** | 端 A 已有 `lb_drel`/`vrel`/TTC；端 B 用 100 ms 前的 10 Hz 数据判 1 m 级阈值不可靠 | 端 B 的 `LateralSafetyEvaluator` 降级为"仅在端 A 未提供数据时的兜底" |
| "想不想超车"（意图与时机） | **端 B（导航语义）** | 只有它知道前方车道推荐、匝道出口 | 端 B 停止做安全裁决，改为提交带理由的请求 |
| 是否允许执行（安全门） | **端 A，且 panda 兜底** | 决策不能依赖 Wi-Fi；断链必须自动回到"标准 ACC/无变道" | 端 B 断链时只禁自主请求，不影响端 A 已有逻辑 |
| 驾驶员是否接管 | **端 A**（`steeringPressed`/DM） | 端 B 用方向盘角差判接管会误判 | 端 B 撤销判据只保留 `engaged` 丢失与刹车/油门 |

一句话：**"安全相关的每一个判定，都必须能在没有 Wi-Fi 的情况下继续成立。"** 当前架构里，端 B 既是"请求方"又是"仲裁方"，而端 A 对端 B 的输入毫无鉴权——这是根本问题，不是阈值问题。

### 9.3 回归防护（防止再次出现本次这类缺陷）

```
· schema.toml 出码到 Python/Kotlin（两端编译期即知字段漂移）
· 两端各一条 golden-packet 测试：输入同一段真实抓包 → 断言解析值与单位
· 每条安全裁决写双端对称表测试：输入 (NO_THREAT, UNKNOWN, THREAT) × 档位 0/1/2 → 断言放行/阻断矩阵
· "超时/断连/缺字段"三类异常用例必须在端 B 状态机测试里存在（现全部缺失）
· CI 必跑：端 A `get_torque_params()` 冒烟 + opendbc 车测试；端 B `assembleRelease + lint + test`
· 任何跨仓改动（M-x 工单）必须在 schema.toml 留条目并在两端 CI 变红后才允许合入
```

## 附录 C：结语 —— 这套协同功能现在处于什么状态

**它不是一个"还需要调优的功能"，而是一条"从未在真机上闭合过的链路"。** 三条独立证据指向同一结论：

1. 端 A 的 `torque_data` 冲突让分支**根本起不来**（`get_torque_params()` 抛错，我已复算），也就是说 `cp-custo-amap` 上任何"实测结论"都发生在改动之前；
2. 端 A 的 `SPEED_LIMIT` 与端 B 的命令名**对不上**，说明"巡航调速"这条最容易被验证的功能从未打通；
3. 端 A 的 `blinker` 类型不匹配 + `OVERTAKE` 字符串不匹配，说明双端连"变道请求"的正向路径都没跑通过端到端验证（否则 CANCEL 的 index 要求、`atc_state=3` 反馈、0.0 哨兵这些一定会在第一次实测中暴露）。

因此正确的心态是：**先把"链路是否闭合"证明出来（§9.1 的 E1-E9，全部不需要上路），再谈 MPV 标定，最后才谈性能与体验优化。** 在这个顺序被打乱之前，端 A 里那些"帕里斯帝 NNFF""5 s 防晕车变道""50 ms 撤销"之类的描述，应当从 README 中移除或明确标注为"未实现" —— 安全相关的过度承诺，本身就是缺陷。
