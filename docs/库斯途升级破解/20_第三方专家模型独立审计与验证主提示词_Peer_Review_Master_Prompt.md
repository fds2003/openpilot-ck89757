## 三、你必须严格执行的六大审计维度

请抛弃一切客套和泛泛而谈的赞美，以最严厉、批判性（Critical）的眼光，对以下六个维度进行逐项形式化推演与审查：

### 维度 1：网络拓扑与通信契约正确性 (Networking & Protocol)
- **端口绑定与寻址**：车机监听 7706/5510，C3 监听 7705/5510，C3 发往 7706。该端口矩阵是否存在冲突？能否在 Android 4.4 与 Linux aarch64 之间实现确定性双向闭环？
- **动态 IP 自适应能力**：在车载热点屏蔽 UDP 255.255.255.255 广播、或 DHCP 分配任意网段（`192.168.43.x`、`172.20.10.x`）的工况下，基于 5510 探针捕获 `addr[0]` 动态学习 IP 的方案是否足够健壮？是否存在多车机混淆风险？

### 维度 2：多线程并发与进程生命周期安全 (Threading & Lifecycle)
- **非阻塞性保证**：新增的 `_discovery_responder_thread` 与 `_headunit_cmd_recv_thread` 是否完全独立？是否有任何可能导致 openpilot 100Hz `controlsd` 主循环被阻塞超过 10ms？
- **共享内存与数据竞争**：`SharedData` 类的读写是否线程安全？`public_amap_navi` 向 Cereal 发布消息时，是否存在 `NoneType` 或竞态读脏数据的问题？
- **进程管理**：在 `system/manager/process_config.py` 中将 `amap_navi` 设为 `always_run` 是否合规？与车辆 Offroad 熄火节能策略是否存在冲突？

### 维度 3：变道控制与 TTC 算法数学严密性 (Dynamics & Math)
- **TTC 数学公式与物理量量纲**：后车时距 $\text{TTC} = \frac{d_{rel}}{-v_{rel}}$ 的计算在除以 0、或者后车相对速度为正（远离）时的边界处理是否完备？
- **三级超车门限设计**：激进（1.8s）、常规（2.5s）、保守（3.5s）的门限设定是否符合汽车工程常理？在高速 120km/h 巡航时是否能给驾驶员留出足够的刹车与变道安全裕量？

### 维度 4：功能安全、容灾降级与极端工况保底 (ISO 26262 & Failsafe)
- **驾驶员绝对优先权**：变道全流程中，方向盘扭矩介入（`steering_pressed`）是否能在 20ms 内无条件切断转向扭矩并退回人工？
- **通信断网熔断机制**：如果行驶途中车载 Wi-Fi 突然断开、车机断电或高德闪退，C3 变道逻辑是否会在预设时间内安全锁定，是否可能诱发任何非预期转向（Unintended Steering）？
- **物理障碍刚性阻断**：盲区雷达有车、目标道为交通实线时，变道阻断逻辑是否存在任何能够被绕过的逻辑漏洞？

### 维度 5：Cereal / Cap'n Proto 接口兼容性 (Serialization Compatibility)
- 在 `cereal/custom.capnp` 的 `struct AmapNavi` 末尾追加 `overtakeMode @15` 与 `lidarBehindVdistTime @16`，是否符合 Cap'n Proto 的向下兼容规范？是否会破坏已有日志回放（Log Replay）或旧模块反序列化？

### 维度 6：代码质量、异常处理与边界漏洞 (Edge Cases)
- 检查 Python 源码实现中是否存在未捕获的 Socket 异常、JSON 解析异常、字典 Key 缺失引发的 `KeyError`、浮点数类型转换崩溃等低级缺陷。
