## 三、关键问题（阻断验收结论）

### F‑32‑01（Critical）当前 HEAD 在"空车道"时阻断所有变道
`amap_navi.py:296-304`（`5da9b56` 之后）：
```python
ttc_list = []
for side in ("lb", "rb"):
    d = getattr(self.shared_data, f"main_{side}_drel", None)
    v = getattr(self.shared_data, f"{side}_vrel", None)
    if d is not None and abs(d) > 0 and v is not None and v < -0.1:
        ttc_list.append((abs(d) / 1000.0) / abs(v))
ttc = min(ttc_list) if ttc_list else 0.0      # ← 无后车目标 = 0.0
```
`desire_helper.py:953-962`：
```python
behind_ttc = amapNavi.lidarBehindVdistTime if amap_alive else 0.0
rear_conflict = (behind_ttc <= 0.0) or (behind_ttc < ttc_threshold)
if rear_conflict:
    auto_lane_change_trigger = False
```
**后果**：只要后方**没有正在接近的目标**（空车道、后车同速、后车远离、低速蠕行），`ttc_list` 为空 → `0.0` → `rear_conflict=True` → **所有变道被永久阻断**。这不是 fail-safe，而是把"无目标"和"传感器失效"混为一谈，属于 **fail-closed 到功能不可用**。

- 交通场景下最常见的"空车道"恰恰是被阻断的状态；只有"后方恰有一辆正在接近且 TTC≥门限"的罕见组合才允许变道。
- 报告 Phase 6 用例 2（后车远离 → 99.0 → 安全通过）在**当前 HEAD 上必然失败**（实际输出 0.0 → 阻断）。

**正确设计**：必须把"无目标"与"传感器失效"分开，例如：
```python
lidar_alive = self.shared_data.lidar_l or self.shared_data.lidar_r   # 客户端存活标志
rear_ttc_valid = lidar_alive and (lb_fresh or rb_fresh)              # 数据新鲜度
ttc = min(ttc_list) if ttc_list else (99.0 if rear_ttc_valid else 0.0)
```
消费端保持 `(ttc <= 0) or (ttc < thr)` → 失效阻断、无目标放行。

### F‑32‑02（Critical）报告引用的提交与测试矩阵自相矛盾
- 报告第 5 行明确写 `Commit ca6cb4a`。
- `ca6cb4a` 的实际 TTC 代码：`git show ca6cb4a:selfdrive/carrot/amap_navi.py:302` → `ttc = min(ttc_list) if ttc_list else 99.0`。
- 因此在 `ca6cb4a` 上：
  - 用例 3（雷达丢失 → 0.0 → 阻断）**不可能 PASS**，实际是 99.0 → 放行；
  - 用例 5（执行期复检不受 350 ms 限制）也**不成立**——`ca6cb4a` 仍带 `ll_prob > 0.3` 窗口；
  - 用例 6 的失效语义仍是旧版。
- 在 `5da9b56`（当前 HEAD 的父提交链）上：
  - 用例 3 可以 PASS；
  - 但用例 2（后车远离 → 99.0 → 安全）**必然失败**（实际 0.0 → 阻断），且触发 F‑32‑01。
- **结论**：不存在任何一个单一提交能同时通过报告列出的用例 2 与用例 3。报告要么混用了多个版本的代码，要么测试脚本是**独立重实现**而非调用生产代码。后一种情况下，"ALL_TTC_SAFETY_TESTS_PASS"不能作为生产代码的验收证据。

### F‑32‑05（Major）受测"车机"不是库斯途原厂车机

- 设备序列 `DU2SSE14BK038094` 与 1080×1920 分辨率更像手机/平板，而非原车机。
- **结论**：本次内存压测（PSS 15.5MB）与 UI 测试**没有在目标车机上完成**，不能支撑"倒车影像 140MB 安全缓冲"的结论；需要在真实 960×1280 / 350MB 车机上复测。

## 六、核验寄语

这份验收报告的可信度**两极分化**：一端是真实截图、真实端口契约、真实 CANCEL 实现、真实米制遥测——这些都能复核，值得肯定；另一端是 TTC 测试矩阵与所引用提交互相矛盾、产物指纹对不上、受测设备不是目标车机、7706 监听来源无代码依据。**"100% 通过"的结论建立在几处无法自洽的证据之上，因此不成立。**

更严重的是：为了让用例 3（雷达失效→阻断）通过而把"无目标"改成 `0.0`，直接导致空车道无法变道（F‑32‑01）。这说明安全逻辑的"失效态"与"无目标态"还没有被正确区分——这恰恰是后车 TTC 门禁最核心的一条语义。**在把这两者分开之前，不应上实车；而分开之后，用例 2 与用例 3 才能同时成立，验收报告也才有意义。**
