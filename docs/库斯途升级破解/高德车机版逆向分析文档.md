## 1. 背景与目标

### 1.1 需求

车机（Android 4.4.3）需要高德地图车机版具备「**原包名悬浮窗**」功能：

- 高德地图退到后台后，在车机首页（Launcher）以一个小窗口继续显示地图
- 使用**原始包名** `com.autonavi.amapauto`（保持与原版一致，可覆盖安装、保留数据）
- 可通过广播消息控制悬浮窗显示/关闭

参考实现：`高德地图车机版7.5.0.600082原包名悬浮(靓华修改).apk`（可正常工作）

目标版本：
- `Auto_9.1.0.600087_release_signed.apk`（官方原版）
- `Auto_9.5.0.600013_release_signed.apk`（官方原版）

### 1.2 车机环境约束

| 约束项 | 值 | 影响 |
|--------|-----|------|
| Android 版本 | 4.4.3（API 19） | minSdk > 19 的 APK 无法安装 |
| CPU 架构 | armeabi-v7a | 无 arm64-v8a 支持 |
| 系统已破解 | 是 | 可安装非官方签名 APK |
| 原有版本 | 7.5.0 靓华修改版 | 需保持数据兼容 |

**直接结论**：9.5.0（minSdk 21 + arm64-v8a）**不可用**，直接排除。

### 1.3 分析路径

```
7.5.0 靓华修改版（可工作）
   │  ① 逆向其修改内容 → 发现两处改动：
   │     a) 悬浮插件（libtouka.so + Java 壳）
   │     b) Java 层签名校验绕过（l90.d → return true）
   ↓
尝试移植到 9.1.0 / 8.5.0
   │  ② 照搬 ①b 的 Java 层绕过 → 黑屏
   ↓
深入分析签名校验机制
   │  ③ 排除法定位：Java 层 + native 层双重校验
   ↓
对比 8.5.0 靓华修改版（可工作）
   │  ④ 发现其使用了 ApkSignatureKillerEx（父类注入 + xHook）
   │  ⑤ 其悬浮插件也升级为第二代（libToukaFloatPlugin.so）
   ↓
找到根本方案
```

### 1.4 术语表

| 术语 | 说明 |
|------|------|
| **靓华修改版** | 车友圈流传的第三方修改版，作者署名"靓华" |
| **原包名** | 保持 `com.autonavi.amapauto`，未改包名 |
| **悬浮窗** | 地图退后台后以小窗口形式继续显示在 Launcher 上 |
| **黑屏** | 应用启动成功、Surface 已创建，但地图内容不渲染 |
| **ApkSignatureKillerEx** | 开源项目（github.com/L-JINBIN/ApkSignatureKillerEx），运行时签名欺骗 |
| **xHook** | 爱奇艺开源的 PLT Hook 库（v1.2.0） |
| **PLT Hook** | 修改 GOT/PLT 表，劫持动态库函数调用 |

### 2.3 渲染引擎 so 大小【静态】

| 版本 | libAutoDice.so |
|------|---------------|
| 7.5.0 | 32,631,344 字节 |
| 8.5.0 | 40,855,852 字节 |
| 9.1.0 | 44,875,356 字节 |

**推断**：从 7.5.0 到 8.5.0 增长了 8.2 MB，与签名保护机制的加强在时间上吻合（见 4.5）。但经字符串排查，**校验逻辑并不在 libAutoDice.so 中**（见 4.5 排查表）。

### 2.4 三个修改版的实际改动方式对比【静态】★核心发现

这是本次分析的**最关键发现**：两代靓华修改版采用了**完全不同的技术路线**。

| 对比项 | 7.5.0 靓华 | 8.5.0 靓华 |
|--------|-----------|-----------|
| **签名处理** | `l90.d()` 改为 `return true`（Java 层绕过） | **`y80.d()` 完全未改**，改用父类注入 + xHook |
| **Application 基类** | `Landroid/app/Application;`（原始） | `Lbin/mt/signature/KillerApplication;`（注入） |
| **Hook 库** | 无 | `lib/armeabi-v7a/libSignatureKiller.so`（30,768 字节） |
| **Hook 数据** | 无 | `assets/SignatureKiller/origin.apk`（22,989 字节） |
| **悬浮插件（第一代）** | `tech/touka/plugin/amap/` + `smali/touka/` + `libtouka.so` | 无 |
| **悬浮插件（第二代）** | 无 | `tech/touka/floatplugin/` + `libToukaFloatPlugin.so` |
| **悬浮 so 大小 / API** | 133,468 B / API 19 | 134,708 B / API 19 |
| **Hook so API** | — | 30,768 B / **API 17** |
| **签名证书** | AOSP platform testkey | ANDROID（普通签名） |

**结论**：作者（靓华）在遇到 8.5.0 的 native 层校验后，**放弃了 Java 层绕过路线**，改用通用的运行时 Hook 方案。这印证了本文档第 4、5 节的结论。

**【推断】双 SurfaceView 的用途**：

| 字段 | 推测角色 |
|------|---------|
| `a:SurfaceView` | **原始**地图 SurfaceView（留在 Activity 中） |
| `b:SurfaceView` | **悬浮窗**中新建的 SurfaceView（用于承接渲染） |
| `c:ViewGroup` | Activity 中的地图容器（用于查找/回滚） |

这意味着实现可能**不是"搬运同一个 View"**，而是**新建一个 SurfaceView 挂到 WindowManager，并让地图引擎把画面同时渲染到两个 Surface**（Android 的 `Surface` 支持多消费者时需 `IGraphicBufferProducer` 的多路分发）。

**【推断】`touka/c` 的方法语义**：

| 方法 | 推测作用 |
|------|---------|
| `a()` | 创建/初始化窗口 |
| `c(Context)` | 注册广播接收器 |
| `d(Intent)` | 处理广播 Intent（3416 字节，最大函数） |
| `e()` | 销毁/清理 |
| `b()` | 单例获取 |

#### 4.1.2.2 `checkPackageSign` 在**原版**中的角色

| 可能性 | 评估 |

| native 代码通过 JNI 反向调用 | **最可能** —— `Sign` 类中还有一个未被 Java 调用的 `public native sign(String)String`，说明 native 侧持有 `Sign` 的引用 |
| 其他 Java 类调用 | 未发现 |

**【推断】**native 层（渲染引擎初始化流程）通过 JNI 反查 `Sign` 类并调用 `checkPackageSign(signInfo)` 完成校验——这正好解释了为什么 `signInfo`（Java 侧算出的 MD5）对 native 校验是必需的（见 5.1 尝试 1/2 的黑屏原因）。

3. 校验逻辑很可能服务于 `AutoLoader` / `libturbo.so` 的加载流程（崩溃点 `AutoLoader.NativeSetStartUpInfo` 是重要线索）

**★ 重要的逻辑闭环**：`Sign.checkPackageSign(String)Z` 是一个 **JNI native 方法**（`Sign.smali:34`）。Java 代码**从不调用它**。它在 native 侧被**反向回调**。因此 native 校验的**第一环**几乎肯定就是这个回调——native 代码在渲染引擎初始化时调用 `Sign.checkPackageSign(signInfo)`，比对失败则跳过 `InitEgl`。

**▲ 这一发现修正了此前的判断**：native 校验**并非**"完全独立的另一套逻辑"，而是**通过 JNI 回调复用了 Java 侧算出的 `signInfo`**。这解释了：
- 为什么"尝试 1/2"（跳过 `getPackageSign`）会黑屏——`signInfo` 为空，native 比对必然失败
- 为什么"尝试 4"（硬编码 `signInfo`）也黑屏——硬编码的值是**修正前**记录的 MD5，与 native 期望的格式/内容不符（见 5.2 的类名映射错误）

### 5.2 尝试 4 失败的独立原因【推断】

`3f9eaea4f2d4285c2ddbbda739136479` 是 **MINIMAP 证书 DER 的 MD5**。但在 9.1.0 中：

| 版本 | MD5 工具类 | 方法 |
|------|-----------|------|
| 7.5.0 | `Ltj0;` | `a([B)String` |
| 8.5.0 | `Lgj0;` | `b([B)String` |
| 9.1.0 | `Ljj0;` | `b([B)String` |

**本应使用 `Ljj0;->b([B)`**，但记录中的硬编码值来自更早的分析，**方法名/类名映射存在版本错配的可能**。此外，`getPackageSign` 取的是 `signatures[0].toByteArray()`（**证书 DER**，非整包签名），MD5 计算方式需与 `jj0.b` 完全一致（大小写、补零）。任一处不符即失败。

### 5.3 关键技术验证矩阵【实测】

| 实验 | dex | 签名 | 现象 |
|------|-----|------|------|
| 原始 APK + 原始签名 | 原版 | MINIMAP_ | ✅ 正常 |
| 原始 dex 重签名 | 原版 | AOSP | ❌ `UnsatisfiedLinkError` 崩溃 |
| 修改 dex + Java 层绕过 | 修改 | AOSP | ❌ 黑屏（不崩溃） |
| **7.5.0 靓华** | 修改（`l90.d → true`） | AOSP | ✅ **正常** |
| **8.5.0 靓华** | 修改（`y80.d` 未改） | ANDROID | ✅ **正常** |
| 悬浮插件单独加（不改签名校验） | 修改 | AOSP | ❌ 崩溃 |

**核心结论**：

1. **7.5.0 只有 Java 层校验** → 改 `l90.d` 返回 true 即可（靓华的做法）
2. **8.5.0 / 9.1.0 有 native 层校验** → Java 层任何改法都黑屏
3. **native 校验通过 JNI 反向调用 `Sign.checkPackageSign`**（见 4.2.3）
4. 因此必须让**所有**校验点看到**一致的原始签名** → 只能靠运行时 Hook

- 只对**通过 PLT 间接调用** `open` 的代码生效
- 直接 `syscall(SYS_openat, ...)` 的代码**不受影响**

### 7.4 Python ELF 分析片段

**提取动态符号（JNI 导出）**：

```python
import struct

def parse_elf_dynsym(path):
    d = open(path, "rb").read()
    assert d[:4] == b"\x7fELF"
    is64 = d[4] == 2

    # 节表偏移
    if is64:
        e_shoff   = struct.unpack_from("<Q", d, 0x28)[0]
        e_shentsize, e_shnum, e_shstrndx = struct.unpack_from("<HHH", d, 0x3a)
    else:
        e_shoff   = struct.unpack_from("<I", d, 0x20)[0]
        e_shentsize, e_shnum, e_shstrndx = struct.unpack_from("<HHH", d, 0x2e)

    sections = []
    for i in range(e_shnum):
        off = e_shoff + i * e_shentsize
        if is64:
            name, typ, flags, addr, offset, size, link, info, align, entsize = \
                struct.unpack_from("<IIQQQQIIQQ", d, off)
        else:
            name, typ, flags, addr, offset, size, link, info, align, entsize = \
                struct.unpack_from("<IIIIIIIIII", d, off)
        sections.append(dict(name=name, type=typ, addr=addr, offset=offset,
                             size=size, link=link, entsize=entsize))

    shstr = sections[e_shstrndx]
    def sname(o):
        p = shstr["offset"] + o
        return d[p:d.index(b"\0", p)].decode()

    dynsym = next(s for s in sections if s["type"] == 11)   # SHT_DYNSYM
    dynstr = sections[dynsym["link"]]
    def dname(o):
        p = dynstr["offset"] + o
        return d[p:d.index(b"\0", p)].decode()

    out = []
    n = dynsym["size"] // dynsym["entsize"]
    for i in range(n):
        off = dynsym["offset"] + i * dynsym["entsize"]
        if is64:
            nm, info, other, shndx, val, sz = struct.unpack_from("<IBBHQQ", d, off)
        else:
            nm, val, sz, info, other, shndx = struct.unpack_from("<IIIBBH", d, off)
        if nm:
            out.append((val, sz, dname(nm)))
    return out

for addr, size, name in parse_elf_dynsym(r"D:\Temp\amap910-check\libtouka.so"):
    print(f"0x{addr:x}  {size:>6d}  {name}")
```

### 8.3 4.4.3 兼容性专项检查【部分已验证】

`KillerApplication.killPM` 中与 Android 版本相关的代码：

```smali
.line 83
sget v4, Landroid/os/Build$VERSION;->SDK_INT:I
const/16 v6, 0x1c                    # 28
if-lt v4, v6, :cond_0                # 只有 API >= 28 才执行
invoke-static {v4}, Lorg/lsposed/hiddenapibypass/HiddenApiBypass;->addHiddenApiExemptions(...)
:cond_0
```

**在 Android 4.4.3（API 19）上**：
- `SDK_INT = 19 < 28` → **跳过** `HiddenApiBypass` → ✅ 不依赖该类
- `PackageInfo.CREATOR` 的反射替换 → 4.4.3 上 `CREATOR` 是 public static final，`setAccessible` 后 `set()` 可能失败（final 字段）→ ⚠️ **需实测**
- `PackageManager.sPackageInfoCache` → 4.4.3 上**不存在**该字段 → `findField` 抛 `NoSuchFieldException` → 被 `catchall_0` 捕获 → **静默跳过** → ✅ 无害
- `Parcel.mCreators` / `sPairedCreators` → `sPairedCreators` 是 Android 10+ 才有的 → 静默跳过 → ✅ 无害
- `loadLibrary("SignatureKiller")` → **这是真正的依赖**：需要 `libSignatureKiller.so` 能在 4.4.3 上加载

**★ 关键项已实测**：`libSignatureKiller.so` 的 `minSdkVersion`（ELF `.note.android.ident` 段）**已解析验证**。

**解析方法**（`.note.android.ident` = `NT_GNU_ABI_TAG`，name = `"Android\0"`，desc 前 4 字节 = API level）：

```python
import struct
d = open("libSignatureKiller.so", "rb").read()
off = d.find(b"Android\x00") - 12
namesz, descsz, ntype = struct.unpack_from("<III", d, off)
desc_off = off + 12 + ((namesz + 3) // 4) * 4
api = struct.unpack("<I", d[desc_off:desc_off + 4])[0]
print("API level:", api)
```

**三个 so 的解析结果**：

| so | `.note.android.ident` API level | 4.4.3（API 19）可加载 |
|----|-------------------------------|---------------------|
| `libSignatureKiller.so` | **17** | ✅ **可以**（17 ≤ 19） |
| `libtouka.so` | **19** | ✅ 可以（19 = 19） |
| `libToukaFloatPlugin.so` | **19** | ✅ 可以（19 = 19） |

**结论**：三个 so **全部声明了 ≤ 19 的 API level**，在 Android 4.4.3 上均可正常加载。

- NDK 链接时声明 API 17 说明 `libSignatureKiller.so` 有意兼容很老的系统
- 两个悬浮插件 so 声明 API 19，正好对应车机的 4.4.3

**仍未验证的 4.4.3 兼容点**：`PackageInfo.CREATOR` 在 4.4.3 上是 `public static final`，反射 `Field.set()` 修改 final 字段的行为在 Dalvik（4.4.3 用 Dalvik，非 ART）上需实测。若失败，`catch_0` 会把异常包装成 `RuntimeException` 抛出 → 应用崩溃。**这是上车前的头号风险点**。

## 10. 工具链安全策略拦截记录

### 10.1 问题描述

在本次分析中，有 **5 类操作**被 Claude Code 的安全策略拦截，导致部分步骤**未能由 AI 直接执行**。

### 10.2 这是什么安全策略？

**★ 重要澄清：这不是 Windows 11 的安全功能，关闭 Windows 的任何设置都无法解除。**

| 对比项 | 说明 |
|--------|------|
| **策略归属** | Claude Code（AI 工具）**自身**的运行时安全分类器 |
| **运行位置** | **服务端 / Harness 层**，不在你的电脑上 |
| **触发时机** | 每次工具调用（Bash / Write / Edit 等）执行**之前** |
| **与 Windows 无关** | 不是 Defender、SmartScreen、UAC、AppLocker、WDAC、Smart App Control、核心隔离中的任何一个 |
| **能否本地关闭** | ❌ **不能**。注册表、组策略、Windows 设置均无效 |

**为什么和 Windows 无关**：
- 拦截发生在**工具调用被批准之后、实际执行之前**
- 即使在纯 Linux 环境（如 WSL、Docker）中使用同样的工具，同样会被拦截
- 它的判断依据是**操作内容的语义**（如"是否在向二进制注入第三方 Hook 代码"），而非本地进程行为

**★ 与 Claude Code 权限系统的区别**（容易混淆）：

| 机制 | 作用 | 可配置 |
|------|------|--------|
| **权限系统**（`/permissions`、`settings.json` 的 `allow` 列表、`--dangerously-skip-permissions`） | 决定**是否弹窗询问**你 | ✅ 可配置 |
| **安全分类器**（本次拦截的来源） | 决定**这个操作本身是否允许** | ❌ **不可配置** |

即使你把某条命令加进了 `allow` 列表（不再弹窗），分类器仍然可以拦截它。

### 10.3 本次实际被拦截的操作

| # | 类目 | 被拦截的操作 |
|---|------|-------------|
| 1 | `[Third-Party Attack]` | 向高德 APK 注入第三方 Hook 代码（`KillerApplication` + `libSignatureKiller.so`） |
| 2 | `[Credential Leakage]` | 处理/写入签名证书相关材料（`platform.pk8` / `.p12`） |
| 3 | `[Untrusted Code Integration]` | 集成 GitHub 下载的未验证第三方二进制 |
| 4 | `[Self-Modification]` | 修改 APK 自身的校验逻辑（`Sign.smali` / `b90.smali` 等） |

## 11. 结论与后续

### 11.1 核心结论

| # | 结论 | 证据等级 |
|---|------|---------|
| 1 | **悬浮窗机制**：两代实现在 9.1.0 上均有效（`MainMapActivity` 未改名） | 【静态】 |
| 2 | **签名校验演进**：7.5.0 仅 Java 层 → 8.5.0/9.1.0 增加 native 层 | 【实测】 |
| 3 | **Java 层绕过在 8.5.0+ 无效**（4 次尝试全部黑屏） | 【实测】 |
| 4 | **原版 `Sign.checkSign()` 就返回 true**（不校验）；**靓华版反而新增了 native 校验调用** | 【静态】 |
| 5 | **native 校验通过 JNI 反向调用 `Sign.checkPackageSign`** 复用 Java 侧算出的 `signInfo` | 【推断】 |
| 6 | **正确方案是 ApkSignatureKillerEx**：父类注入 + `CREATOR` 替换 + xHook | 【静态】 |
| 7 | **靓华 8.5.0 采用该方案**，且 `y80.d()` 完全未改 | 【静态】 |
| 8 | **9.5.0 不可用**：minSdk 21 + arm64 | 【静态】 |
| 9 | **9.1.0 minSdk = 15**，车机可安装 | 【静态】 |

### 11.2 与早期结论的修正

本文档在深入分析后，**修正了以下早期判断**：

| 早期判断 | 修正后 | 依据 |
|---------|--------|------|

## 附录 B：Java 层悬浮窗备案实现

**位置**：`E:\汽车\库斯途升级破解\java-float-window\`
**状态**：备案中，尚未实测

### B.1 为何需要备案

逆向 `libtouka.so` 后发现其设计缺陷：

| 缺陷 | 影响 |
|------|------|
| 类名硬编码 `MainMapActivity` | 高德重构类名 → 悬浮窗**静默失效** |
| 无防抖 | 地图快速切换 → 悬浮窗**闪烁** |
| 生命周期/广播双路控制无**统一**状态机 | 两路各自持有 `AtomicBoolean`，可能冲突 |
| native 实现不可改 | 无源码，优化需 patch 二进制 |

> **修正说明**：早期认为 libtouka.so"无状态机"——实际 `touka/c` 中有 2 个 `AtomicBoolean`（见 3.2.6）。真正的缺陷是**生命周期路径与广播路径各持一套状态，互不感知**。

### B.2 实现对照

| libtouka.so（native） | Java 层实现 | 改进 |
|----------------------|-----------|------|
| `touka.a.a(Application)` | `FloatWindowManager.init(Application)` | 同 |
| `touka.b`（7 个生命周期回调） | `MapLifecycleCallbacks` | 类名**模糊匹配** |
| `ControlReceiver.onReceive` | `ControlReceiver` | 同 |

| 硬编码 `=="MainMapActivity"` | `contains("Map") \|\| contains("Navi")` | **抗重构** |

### B.4 三个核心改进的代码

**① 类名模糊匹配**（抗高德重构）：

```java
private boolean isMapActivity(Activity activity) {
    if (activity == null) return false;
    String name = activity.getClass().getSimpleName();
    return name.contains("Map") || name.contains("Navi");
}
```

**② 防抖 300ms**（防闪烁）：

```java
private static final long DEBOUNCE_MS = 300;

private final Runnable mShowRunnable = new Runnable() {
    @Override public void run() { doShowFloatWindow(); }
};

private void requestShow() {
    mHandler.removeCallbacks(mHideRunnable);
    mHandler.postDelayed(mShowRunnable, DEBOUNCE_MS);
}
```

**③ 手动模式标志**（防广播/生命周期冲突）：

```java
private boolean mManualMode;

// 广播触发时
private void onReceive(Context ctx, Intent intent) {
    mManualMode = true;           // 抑制生命周期自动控制
    if (ACTION_SHOW.equals(intent.getAction())) requestShow();
    else if (ACTION_CLOSE.equals(intent.getAction())) requestHide();
}
```
