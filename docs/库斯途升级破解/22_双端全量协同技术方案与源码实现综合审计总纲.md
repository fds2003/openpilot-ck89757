## 第一部分：全盘系统工程观与车机底层性能约束剖析

本工程不是脱离硬件的普通 App 开发，也不是通用的开源自动驾驶算法演练，而是针对**特定车辆、特定老旧车机平台与高性能智驾芯片**构筑的强实时、高安全车载协同异构系统。

### 1.1 现代库斯途原厂车机系统底层性能瓶颈与版本原因 (Android 4.4 Dalvik)
北京现代库斯途（2021~2024款）车机基于百度 Apollo 深度定制的原厂车机系统，其底层硬件与操作系统具备极端的物理局限性：
1. **处理器与 GPU 性能贫瘠**：主控芯片为恩智浦 **NXP Freescale i.MX6 Quad-Core（4核 ARM Cortex-A9 @ 1.0 GHz）**，搭配 Vivante GC2000 图形处理器。该芯片硬件 2D/3D 像素填充率极低，**不支持 Vulkan，嵌套的 `layout_weight` 会触发反复递归测量（Double Measure Pass），直接导致 UI 卡死**；
2. **物理运行内存（RAM）2.0 GB**：依据 2026-10-24 原厂车机实测（/proc/meminfo：MemTotal 2,059,512 kB ≈ 2.0 GB、MemFree 152,092 kB ≈ 150 MB），主板为 2.0 GB；早期"1GB / 扣除显存后可用 350~400MB"的表述有误，已按 32_RAM口径统一裁决 修订。注意 MemFree 为瞬时空闲值，不等于系统可用上限；
3. **老旧 Dalvik 虚拟机（非 ART）的严苛限制**：
   - **JIT 预校验（Pre-verification）致命闪退**：Dalvik VM 在加载 DEX 类时，会对方法的每一处字节码进行静态引用检查。如果代码中直接引用了 Android 5.0+（API 21+）或 Android 8.0+（API 26+，如 `NotificationChannel`、`startForegroundService`），Dalvik 会在类加载瞬间直接抛出 **`java.lang.VerifyError`** 或 **`NoClassDefFoundError`** 导致进程瞬间猝死；
   - **`GC_FOR_ALLOC` 全局挂起停顿（Stop-The-World）**：Android 5.0+ 的 ART 虚拟机具备并发压缩与并行 GC，而 Android 4.4 的 Dalvik 虚拟机每次触发垃圾回收都会完全挂起所有线程（STW 达 30ms ~ 80ms）。如果高频 UDP 遥测数据包在每秒 20~50 次的循环中不断 `new` 对象，Dalvik 堆将迅速打满并疯狂 GC，造成车机 UI 严重掉帧与丢包；
   - **MultiDex 与 65,536 方法数限制**：Dalvik 的 LinearAlloc 缓冲区仅有 5MB 大小，方法数超过 64K 或 DEX 结构不良会导致安装时崩溃。

### 1.2 R 挡倒车影像保活与内存约束（按 2.0GB 口径重算，见 32 号裁决）
* **倒车影像（AVM/RVC）的生命线地位**：库斯途是一台近 5 米长的大车，驾驶员挂入倒车挡（R 挡）时，原厂倒车影像/全景影像服务（/system/bin/reverse_service）必须在 0.5 秒内抢占屏幕并显示画面；
* **低内存杀手（LMK）风险（按 2.0GB 实测口径重算）**：
  - 高德地图车机版导航时常驻约 209 MB；原版伴侣应用实测可达 250MB+，合计约 459 MB；
  - 在 2.0 GB 总内存下，459 MB 并不必然触底。旧文"209 + 250 = 459 > 350MB 可用"的推导建立在错误的 350MB 上限上，已撤回；
  - 真正的约束是实测 MemFree 约 150 MB 的瞬时空闲、Android 4.4 LMK 阈值，以及 R 挡影像服务抢占屏幕的 0.5 秒时序；结论需以实机 LMK 日志与 R 挡时序实测为准（见 32 号裁决第六节）。
* **内存控制目标（口径统一后）**：AmapNavi-Reborn 的 PSS 以实测 dumpsys meminfo TOTAL PSS 为准（25 / 28 号报告实测 15.2 / 15.5 MB）。旧文的"常驻 3.5MB / 峰值 35~55MB / 140MB 缓冲带 / 50MB 红线"均为旧口径数字，不再作为验收依据。

## 第三部分：车机端 (Android 4.4) 深度重构思路与实现方案

### 3.1 原版核心缺陷分析 (内存暴涨 250MB/高频GC顿挫/VerifyError崩溃/返回键崩溃)
1. **内存暴涨 250MB+（旧口径推论已撤回）**：原版 APK（V1.3.6.9）体积高达 31.2MB，内部打包了大量无用测试图片、OkHttp 全套类库及未精简的第三方 SDK。旧文称"车机仅剩 350MB 运存、原版一开飙至 450MB+ 必然触发 LMK"，该前提与 2.0 GB 实测口径不符（见 32 号裁决），不再作为结论；R 挡影像黑屏风险改以实机 LMK 日志与 0.5 秒抢占时序实测判定；
2. **高频 UDP 数据包造成严重 GC 顿挫**：每秒 20~50 个 UDP 遥测包均采用 `org.json.JSONObject` 反复反序列化为 `HashMap`，在 Dalvik 虚拟机中产生海量碎片对象，引发高频 `GC_FOR_ALLOC` 停顿（每次停顿 30~80ms，车机操作极度卡顿）；
3. **低版本 Android 4.4 兼容性崩溃**：
   - 源码中直接使用了 API 26+ 的通知渠道（`NotificationChannel`）与 `startForegroundService` API，未做反射或版本隔离，Dalvik JIT 预校验阶段直接抛出 `java.lang.VerifyError` 崩溃；
   - 在主界面点击物理返回键退出时，阻塞中的 UDP 套接字被强制关闭未捕获 `SocketException`，导致崩溃闪退；
4. **UI 排版挤压变异**：原版在 960x1280 竖屏上采用单列线性排列，控件严重被挤出屏幕，必须大幅滑动，且操作按键错位。

### 3.2 核心重构设计思路 (Zero-Bitmap / FastParser / In-Window SAA / 8x8免滑动栅格)
1. **纯矢量去位图架构 (Zero-Bitmap Architecture)**：

#### ① 零对象分配流式 UDP 解析器
* **源码路径**：`AmapNavi-Reborn/app/src/main/java/tech/touka/amapnavi/data/udp/CarrotTelemetryParser.kt`
* **核心实现**：
```kotlin
package tech.touka.amapnavi.data.udp

object CarrotTelemetryParser {
    // 零对象分配：直接在接收到的原始 String 上以字符游标切片，完全杜绝 HashMap/String 对象分配
    fun parse(payload: String): CarrotTelemetry {
        val vEgoKph = extractDouble(payload, "\"v_ego_kph\":", 0.0)
        val steerAngle = extractDouble(payload, "\"steer_angle\":", 0.0)
        val lead1 = extractBoolean(payload, "\"lead1\":", false)
        val drel = extractDouble(payload, "\"drel\":", 0.0)
        val vrel = extractDouble(payload, "\"vrel\":", 0.0)
        val behindTtc = extractDouble(payload, "\"lidar_behind_vdist_time\":", 99.0)
        val leftLineType = extractInt(payload, "\"left_line_type\":", 0)
        val rightLineType = extractInt(payload, "\"right_line_type\":", 0)

        return CarrotTelemetry(
            vEgoKph = vEgoKph,
            steerAngle = steerAngle,
            lead1 = lead1,
            drel = drel,
            vrel = vrel,
            lidarBehindVdistTime = behindTtc,
            leftLineType = leftLineType,
            rightLineType = rightLineType
        )
    }

    private fun extractDouble(src: String, key: String, defaultVal: Double): Double {
        val idx = src.indexOf(key)
        if (idx == -1) return defaultVal
        var start = idx + key.length
        while (start < src.length && src[start] == ' ') start++
        var end = start
        while (end < src.length && (src[end] in '0'..'9' || src[end] == '.' || src[end] == '-')) end++
        return src.substring(start, end).toDoubleOrNull() ?: defaultVal
    }
}
```

## 第四部分：C3 端 (Comma 3 / openpilot) 深度改造与实现方案

### 4.1 原版 C3 代码缺陷分析 (进程注释假死/端口错配失联/盲区变道无门禁)
1. **守护进程被注释禁用**：`system/manager/process_config.py:144` 带有前置 `#`，openpilot 从未启动 `amap_navi.py`，端口完全不开放；
2. **UDP 端口配置错位**：`amap_navi.py` 内部将遥测数据误发往 `(ip, 7705)`，而车机端在 7706 监听；车机发往 7705 的控制指令 C3 本地又未开监听，导致通信双向失联；
3. **局域网 DHCP IP 漂移脆弱性**：依赖广播地址，在手机热点屏蔽广播时直接断联；
4. **变道逻辑无后车时距门禁**：`desire_helper.py` 只要视觉见虚线就直接变道，后方车辆即便以 140km/h 极速逼近也不会阻断，存在严重追尾安全隐患。

---

### 4.2 协同通信架构与三级超车门禁设计思路
1. **解禁进程并挂载 `always_run`**：通过 openpilot `manager` 实现全生命周期常驻与崩溃 3 秒自愈；
2. **UDP 5510 探针动态 IP 学习**：C3 监听 5510，收到车机 `c3_ping` 瞬间截获车机实际单播 IP，开启单播与广播双通道推流；
3. **UDP 7705/7706 严格对齐**：7705 独立线程接收车机控制指令，7706 定频 20Hz 向车机推送 81 项遥测；
4. **三级超车模式与后车 TTC 数学门禁**：
   $$\text{TTC} = \frac{d_{behind}}{|v_{behind} - v_{ego}|}$$
   - 激进模式（0）：门限 $1.8\text{ s}$；
   - 常规模式（1）：门限 $2.5\text{ s}$（默认）；
   - 保守模式（2）：门限 $3.5\text{ s}$；
   当 $\text{TTC} < \text{门限}$ 时，强制 `auto_lane_change_trigger = False` 刚性阻断变道，并播报语音警告。

### 5.2 极端工况容灾与驾驶员绝对优先权证明 (ISO 26262)

1. **驾驶员物理接管绝对优先（20ms 熔断）**：
   变道执行全流程中，方向盘扭矩传感器检测到反抗力矩（`steering_pressed > 1.2Nm`），`desire_helper.py` 在下一帧（$\le 20\text{ms}$）立即无条件强制将变道状态机置为 `off`，完全交还人工驾驶；
2. **车载 Wi-Fi 断网与车机断电安全降级**：
   若 Wi-Fi 信号丢失超过 1.0 秒，C3 变道计时器归零，变道使能自动失效，openpilot 平稳退回单车道居中巡航，绝无非预期转向；
3. **物理盲区与实线刚性阻断**：
   盲区雷达有车（`left_blindspot`）、侧向激光雷达告警（`0x04`）、交通实线（`0x08`）时，状态机硬性封锁变道并持续语音告警。
