## 一、综合评审结论 (Overall Verdict)

# 🟠 [NEEDS REVISION] —— 双端架构方向正确，但存在 1 项 Critical 级双端契约冲突 + 3 项 Major 安全/兼容缺陷，必须修正后方可上实车

**核心评语（决定性事实）**：
1. 车机端 C3 端源码均可读、可构建、架构分层（`RelayEngine` 单向数据流 + `ViewFlipper` 同窗设置 + `CoreLibraryDesugaring` + `armeabi-v7a`）整体是**扎实的**，内存红线目标（PSS 3.5MB 常驻）方向正确。

## 四、极端边缘工况推演与反例压力测试 (Stress Tests)

### 场景 A（高负荷内存极限 + R 挡倒车）
高德复杂立交三维渲染（209MB）+ 伴侣应用收 UDP 遥测风暴 + 挂 R 挡。**现状**：`CarrotUdpClient.kt:77` 每包 `String(...)` 分配，风暴下 Dalvik GC 停顿放大；`KeepAliveService` 前台优先级保住自身，但**伴侣应用内存峰值 35MB 是否真的在 4.4 上不超限需实机 `dumpsys` 复测**。倒车影像（`/system/bin/reverse_service`）抢占 0.5s 是否被 LMK 阻断，取决于总内存：高德 209 + 伴侣峰值 55 = 264 < 可用 350，**理论上有余量**，但**前提是把 B-03 的 String 分配控住**。
**推演结论**：方向安全，需实机 `dumpsys meminfo` 复测 35MB 峰值 + 风暴工况下无 `GC_FOR_ALLOC` 长停顿。

### 场景 B（高速断网 + 后车逼近，变道中）
110km/h 发起变道时热点断电 + 后车接近。**现状**：`carrot_lane_change_count` OVERTAKE 窗口为 **20s**（`desire_helper.py:523`，非总纲 5.2 宣称的 1s）→ **断网 1s 不会使变道计时器归零**，变道窗口最长 20s 仍可能执行。后车门禁走独立雷达链路，若雷达同时失效则 **fail-open**（A-06）。**结论：场景 B 下"断网 + 后车"双失效时存在非预期变道窗口**，必须靠 3.3 的 fail-safe + OVERTAKE 计数心跳超时（C-02）双重封死。

### 场景 C（激光雷达雨雪跳变）
TTC 由 99s 瞬间跳 0.1s 又恢复。**现状**：`lb_vrel` 经 `RadarSpeedEstimator`（4m/s² 限幅 + 0.5s 滑窗）平滑，但 **TTC 直接用原始 `lb_vrel`/`main_lb_drel` 算**（`amap_navi.py:297`，未走滑窗输出），雨雪单帧毛刺可能令 `behind_ttc` 瞬跳 0.1s → `rear_conflict=True` 触发一次变道阻断 + "盲区有车"播报，随后恢复。**结论**：毛刺会导致**一次误阻断**（安全方向，可接受），但**不应反复触发**。建议 3.3 中加 TTC 的**滑动中值滤波（≥2 帧）**防单帧毛刺。
