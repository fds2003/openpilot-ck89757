## 三、未闭环项

### U-01 F-02：TTC fail-open 整体漏修（Critical）

- amap_navi.py:302：ttc = min(ttc_list) if ttc_list else 99.0 —— 雷达无数据 / 后车远离时置 99.0
- desire_helper.py:934：rear_conflict = (behind_ttc <= 0.0) or (behind_ttc < ttc_threshold) —— 99.0 时两条均 False，放行变道
- desire_helper.py:1246：执行期 _ttc = amapNavi.lidarBehindVdistTime if _alive else 0.0，但复检判定含 0.0 < _ttc 下限（见 U-03），消息缺失时同样不中止
- 即触发阶段与执行阶段在"无数据"时都放行，与 fail-safe 目标相反
- 该项在 26_25号整改交付报告独立核验与真伪对照.md 中编号为 F-02，28 号报告的 5 项清单（B-01 ~ B-05 加 P-5）中**完全没有对应项**

### U-02 B-04：门禁未脱离 0.2 秒计数器（Critical）

- desire_helper.py:920 的整段 TTC 门禁仍包在 if self.carrot_lane_change_count > 0: 内
- 车机 RelayEngine 只发 LANECHANGE，该计数为 4 帧（0.2 秒）；OVERTAKE 分支不可达，故 LANE_CHANGE_TIME_MAX 的 20 秒窗口不会进入
- 结论：变道真正执行的数秒内门禁仍不存在。报告 P-4 声称"门禁脱离计数器 + 执行期复检"，只完成了后半

### U-03 新增执行期复检自身是 fail-open（Major）

- desire_helper.py:1240-1253 确实在 LaneChangeState.laneChangeStarting 内注入了复检（B-05 已修），但判定为：
  if (0.0 < _ttc < _thr) and self.lane_change_ll_prob > 0.3
- 问题一：_ttc = 0.0（无效 / 消息缺失）时 0.0 < _ttc 为 False，不中止，与触发阶段 behind_ttc <= 0.0 即阻断的语义相反
- 问题二：ll_prob > 0.3 限制使变道后期（ll_prob 衰减后）不再复检
- 即新增复检比它要补强的触发门禁更宽松
