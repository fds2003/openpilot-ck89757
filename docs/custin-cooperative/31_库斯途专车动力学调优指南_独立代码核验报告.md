## 二、逐项裁决与证据

### 2.1 车型参数：代码可核验部分一致
`opendbc_repo/opendbc/car/hyundai/values.py:445-449`：
```python
HYUNDAI_CUSTIN_1ST_GEN = HyundaiPlatformConfig(
    [HyundaiCarDocs("Hyundai Custin 2023", "All", car_parts=CarParts.common([CarHarness.hyundai_k]))],
    CarSpecs(mass=1690, wheelbase=3.055, steerRatio=17),
    flags=HyundaiFlags.CHECKSUM_CRC8,

```
- **整备质量 1690 kg、轴距 3.055 m** 与文档一致 ✅
- 车长/车宽/车高、满载质量、8AT 齿比、后扭力梁等属**车外事实**，仓库无法核验；建议以厂方维修手册为准。
- `steerRatio=17` 未在文档中出现，但它直接影响 NNFF 映射的适用性（见 2.2）。

### 2.2 NNFF 映射：真实有效，但替代车型偏差需实测
- 映射存在：`substitute.toml:43`；`HYUNDAI_PALISADE.json` 存在；`interfaces.py:41` 确实读取 `TORQUE_SUBSTITUTE_PATH`。
- 但两车参数差异不小：

| 参数 | CUSTIN | PALISADE |
|:---|:---:|:---:|
| 质量 | 1690 kg | **1999 kg** |
| 轴距 | 3.055 m | **2.9 m** |
| 转向比 | 17 | **15.6×1.15 = 17.94** |
| 后轮 | 扭力梁 | 独立多连杆 |

- 转向比接近（17 vs 17.94）是加分项；但质量差 309 kg、轴距差 155 mm、悬架形式不同，NNFF 训练域并不完全覆盖。
- **建议**：上车后采集 10~20 分钟直道/大弯数据，对比 `latAccelFactor` 与实测横向加速度，必要时改映射 `HYUNDAI_SANTA_FE`（1806 kg / 2.766 m / steerRatio 16.55）或自训模型；不要把"映射即完美"写进验收口径。

### 2.3 前馈偏航滞后补偿：未实现
- 全仓搜索 `tau_lead`、`0.15`、`yaw.*lead`、`lead.*yaw`：**无任何命中**（`lateral_planner.py` / `latcontrol_torque.py` / `desire_helper.py`）。
- `lateral_planner.py` 确实被 `plannerd.py` 使用、`lateralPlan` 也被 `controlsd` 订阅，因此"改这个文件"的落点是存在的；但文档只给了公式 $\delta_{lead}=\delta_{planned}+0.15\dot\kappa v$，**没有对应代码、没有插入位置、没有单位换算**。
- **判定**：这是**设计提案**，不是已落地优化。若按字面验收会被误认为已生效。

### 2.4 5.0s 平顺变道：未实现，且选错了变量（Major）
文档代码：
```python
LANE_CHANGE_STEP_CUSTO = 1.2 * DT_MDL
self.lane_change_ll_prob = max(self.lane_change_ll_prob - LANE_CHANGE_STEP_CUSTO, 0.0)
```
代码事实：
- `LANE_CHANGE_STEP_CUSTO` **不存在**，实际仍是 `desire_helper.py:1247` 的 `2 * DT_MDL`；
- 即使按文档数值计算，`1.2*0.05=0.06/帧`，20 Hz 下 1.0→0 只需 **≈0.83 s**，**不是 5 s**；
- 更关键：`lane_change_ll_prob` 在 `modeld.py:486` 只被赋给 `modelV2.meta.laneChangeProb`，而**全仓唯一读取处是 `lateral_planner.py:149` 的一行注释**（`# self.LP.lane_change_multiplier = 0.0 #md.meta.laneChangeProb`）。也就是说，**改这个变量不会改变任何实际轨迹**。
- 变道时长由模型输出的变道轨迹决定；要真正拉长到 5 s，需要改模型 desire/路径规划（`lane_planner_2` / `LateralMpc` 的路径整形或 `lane_change_multiplier`），而不是改 `ll_prob`。
- **0.08 g / 0.05 g/s 限幅**：代码中无任何横向加速度/Jerk 钳制实现（`grep 0.08` 无命中）。
- **附带说明**：从几何上，3.5 m 横移、5 s、最小 jerk 轨迹的峰值横向加速度约 $5.77D/T^2\approx0.81\ \text{m/s}^2\approx0.083g$，与 0.08 g 自洽——**目标值合理，但没有实现**。

### 2.5 `ret.startAccel = 1.0`：生效，但不是"库斯途专属"
`opendbc_repo/opendbc/car/hyundai/interface.py:196-203`：
```python
ret.pcmCruise = not ret.openpilotLongitudinalControl
ret.startingState = False
ret.vEgoStarting = 0.1
ret.startAccel = 1.0
ret.longitudinalActuatorDelay = 0.5
```
- 该赋值**无 `if candidate == CAR.HYUNDAI_CUSTIN_1ST_GEN` 条件**，对本分支所有现代车型生效。
- 若本分支只服务库斯途，功能结果相同；但文档给出的代码片段与实际代码不一致，且一旦复用到其他车型会带来非预期变化。**建议加车型条件，或在文档中如实写明"全局改动"。**

### 2.6 红灯停稳锁零：数据源与机理双重偏差
文档表述：高德红灯倒计时 → `actual_stop_distance = 0.0` → ESC 深压。
代码事实（`selfdrive/carrot/carrot_functions.py`）：
- `trafficState` 来源于 `carrot_functions.py:279-283`（视觉/模型的红绿灯判断），再经 `carrot_man.py:599` 的 `longitudinalPlan.trafficState` 回传；**`amap_navi.py` 中完全没有 red-light/traffic 字段**（`grep traffic amap_navi.py` 无命中）。**高德倒计时从未接入该逻辑。**
- `actual_stop_distance` 是"距停止点的剩余距离偏移"：`:491` 每帧递减，`:493-497` 在 `stop_model_x==1000`（无模型停止目标）时置 0，否则 `stop_dist = stop_model_x + actual_stop_distance`（`:506`）。把它设为 0 的含义是"**停在模型给出的停止点**"，**不是**"锁定更深制动压力"。
- 因此文档把"0.0"理解成"硬锁死防蠕动"是**语义错误**；真实防蠕动来自 `XState.e2eStopped` + 纵向控制，而非该变量归零。

### 2.7 原厂仪表点亮：条件启用，示例代码失真
- 真实函数（`opendbc_repo/opendbc/car/hyundai/hyundaican.py:119-131`）：
  ```python
  def create_lfahda_mfc(packer, CC, blinking_signal):
    values = {
      "LFA_Icon_State": 2 if CC.latActive else 1 if CC.enabled else 0,
      "HDA_Icon_State": 0 if activeCarrot == 3 and blinking_signal else 2 if activeCarrot >= 1 else 0,
      "HDA_VSetReq": 0,
      "HDA_USM": 2,
      "HDA_Icon_Wheel": 1 if CC.latActive else 0,
    }
  ```
  文档示例里的 `HDA_SetSpeed`、`HDA_SysState` **不存在**；实际 `HDA_VSetReq` 恒为 0，**不会同步巡航设定车速**（文档 5.2 的"巡航设定时速同步"不成立）。
- 发送条件（`carcontroller.py:353-355`）：`self.frame % 5 == 0 and self.CP.flags & HyundaiFlags.SEND_LFA.value` → 20 Hz ✅；但 `SEND_LFA` 只在 `interface.py:135-137` 的 `if 0x485 in fingerprint[2]` 成立时置位。
- 库斯途的 `HyundaiPlatformConfig` **未显式声明 `SEND_LFA`**，是否点亮取决于实车相机总线指纹里是否出现 `0x485`。**需在实车 `fingerprint` 日志确认**，不能当作既定事实。
- `LFAHDA_MFC` 的 CAN ID 为 1157 = **0x485** ✅（`hyundai_kia_generic.dbc:1496`）。

### 2.8 温控与功耗：原生行为 + 未实现部分
- `system/hardware/tici/hardware.py:358-375` 的 `set_power_save()` 会：
  - 将 `cpu4~7` 的 `online` 写 0（**下线 4 个大核**）✅；
  - governor 在 `ondemand/performance` 间切换 ✅。
- 但**代码中没有在 Offroad 时把 `force_clk_on`/`force_rail_on` 置 0**；`initialize_hardware()` 反而把它们置 1（`:421-422`）。文档"释放 GPU 供电轨"**未实现**。
- `set_power_save` 由 `system/hardware/hardwared.py:367` 的 `HARDWARE.set_power_save(not should_start)` 调用——**这是 openpilot 原生节能策略**，不是本工程新增的"固化温控"。
- `1.65 W / 39℃` 属实测数据，代码无法核验；需给出测量条件（环境温度、是否开风扇、屏幕亮度）。

### 2.9 CAN 频率描述错误（Minor）
- 文档 1.4："0x340 LKAS11，50Hz"。
- 实际：经典 CAN 分支每帧无条件 `can_sends.append(hyundaican.create_lkas11(...))`（`carcontroller.py:331-334`），`controlsd` 以 `Ratekeeper(100)` 运行 → **LKAS11 为 100 Hz**。
- `0x340` 本身正确（DBC `BO_ 832 LKAS11`，832 = 0x340）✅；LFAHDA 20 Hz ✅。

6. **仪表盘**：先实车确认 `0x485` 出现在 `fingerprint[2]`；并修正文档中的字段名与"巡航车速同步"表述。
7. **温控**：如需 GPU 轨释放，在 `set_power_save(True)` 中补写 `force_clk_on=0`、`force_rail_on=0`，并评估唤醒延迟；否则删除该宣称。

**总判定**：🟠 **[NEEDS REVISION]**。作为"设计指南"其方向（大车力矩、平顺变道、8AT 起步、仪表联动、夏季温控）是合理的；但作为"生产落地级技术规范"和"实施清单"，**6 个模块中仅 1 个真正落地，2 个条件/全局生效，3 个未实现或机理错误**。建议在文档中逐项标注状态，并把 §3.2、§4.3、§5.2 的"已实现"表述改为"待实现/提案"，同时把 §2.3、§3.3 补上真实代码落点，否则后续验收会以"文档说已做"为依据，导致安全与性能预期失真。

> **核验寄语**：这份指南最值得肯定的是 NNFF 映射——它是六项中唯一在代码里真实存在且方向正确的优化。其余五项更像"调优愿望清单"：方向没错，但变量选错（`ll_prob`）、数据源标错（高德 vs 视觉）、条件写错（全局 vs 专车）、实现缺失（偏航超前/横向限幅/GPU 轨）。把状态标清楚、把落点写准，它就会从"好看的方案"变成"可验收的规范"。
