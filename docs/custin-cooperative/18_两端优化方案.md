## 1. BUG-1 — `driver_steering` 从未发送

### 问题

车机端 `OvertakeStateMachine.handleExecuting()` 有双重接管检测：

```kotlin
// OvertakeStateMachine.kt:220-222
val driverIntervened = !car.engaged || car.brakePress ||
    steerDelta > settings.driverSteerThresholdDeg ||
    (car.isDriverSteering && steerDelta > 5.0f)   // ← 依赖此字段
```

`CarrotTelemetryParser.kt:23` 解析 `"driver_steering":` 键，但 C3 端 `make_navi_message()` 全函数 grep 无此字段输出，`car.isDriverSteering` 恒为 `false`。接管检测退化为纯角度门限（≥25°），驾驶员轻推方向盘不触发撤销。

### 修复 — C3 端 `amap_navi.py`

**定位**：`make_navi_message()` → `if self.shared_data.carState:` 块（约第 1795 行）。

`carState` 中 `steeringTorqueEps` 与 `steeringAngleDeg` 符号相反时为驾驶员主动介入。`update_navi_carstate()` 已订阅 `carState`，直接在 `SharedData` 中计算并缓存：

```python
# amap_navi.py — SharedData.__init__() 新增字段（约第 186 行）
self.driver_steering = False   # 驾驶员主动转向标志
```

```python
# amap_navi.py — update_navi_carstate()，紧接 steeringAngleDeg 读取后追加
if hasattr(carState, 'steeringTorqueEps') and hasattr(carState, 'steeringAngleDeg'):
    # 扭矩与转角方向相反 → 驾驶员抵抗 OP 转向
    torque = carState.steeringTorqueEps
    angle  = carState.steeringAngleDeg
    self.shared_data.driver_steering = (
        abs(torque) > 0.5 and          # 忽略噪声扭矩
        (torque * angle < 0)           # 方向相反
    )
```

```python
# amap_navi.py — make_navi_message()，steer_angle 发送后追加
msg['driver_steering'] = self.shared_data.driver_steering
```

**验证**：手动扭方向盘（方向与 OP 期望相反），HUD 应在 ≤100 ms 内显示"驾驶员干预"并撤销变道。

## 2. BUG-2 — `atc_state` 发送有条件盲窗

### 问题

```python
# amap_navi.py:1952-1997
if self.sm.alive['modelV2']:      # ← 条件 1
    ...
    if isOnroad:                  # ← 条件 2
        ...
        msg['atc_state'] = meta.laneChangeState.raw   # 仅此路径发送
```

`modelV2` 进程偶发短暂不 alive（进程重启、热更新）时，`atc_state` 丢失，车机端 `CarrotTelemetryParser` 解析返回默认值 0，`OvertakeStateMachine.handleExecuting()` 无法收到 `atcState==3`（变道完成），只能等待 4 500 ms 超时才能进入 `FINISHING`。

**影响**：每次变道完成后，冷却比实际晚 0~4.5 s 触发；高频变道场景（如连续超车）冷却时序混乱。

### 修复 — C3 端 `amap_navi.py`

把 `atc_state` 移出 `modelV2` 条件块，改为在 `carrotMan` 块中从 `atcType` 字符串派生（`carrotMan` 是稳定可用的 cereal 话题）：

```python
# amap_navi.py — make_navi_message() carrotMan 块内（约第 1934 行）
if self.sm.alive['carrotMan']:
    carrotMan = self.sm['carrotMan']
    msg['desire_speed'] = int(carrotMan.desiredSpeed)
    atc_type = carrotMan.atcType
    road_name = carrotMan.szPosRoadName
    # ... 现有代码保持不变 ...

    # 新增：从 atcType 字符串派生整数 atc_state
    # carrotMan.atcType 枚举字符串：
    #   "none" / "prepare" → 0
    #   "preLaneChange"    → 1
    #   "laneChangeStarting" → 2
    #   "laneChangeFinishing" → 3（变道完成信号）
    if 'laneChangeFinishing' in atc_type:
        msg['atc_state'] = 3
    elif 'laneChangeStarting' in atc_type:
        msg['atc_state'] = 2
    elif 'preLaneChange' in atc_type:
        msg['atc_state'] = 1
    else:
        msg['atc_state'] = 0
```

同时保留 `modelV2` 路径作为二次覆盖（更精准），两者不冲突：后写的覆盖先写的。

**验证**：发起超车后观察车机 HUD Trace，应在车道完成居中后（非超时）出现 `完成结算` 状态条目。

## 3. GAP-1 — 6 个安全参数 KEY 对决策无效

### 问题

`UserSettingsRepository` 定义了以下 KEY：

```kotlin
KEY_FRONT_THRESH_MODE   "lidar_front_dist_mode"
KEY_FRONT_THRESH_VAL    "lidar_front_dist_m"
KEY_REAR_THRESH_MODE    "lidar_rear_dist_mode"
KEY_REAR_THRESH_VAL     "lidar_rear_dist_m"
KEY_FRONT_VREL_TIME     "lidar_front_vrel_time_s"
KEY_REAR_VREL_TIME      "lidar_rear_vrel_time_s"
```

但 `loadOvertakeSettings()` 只读 3 个 KEY，`LateralSafetyEvaluator` 的全部阈值硬编码：

```kotlin
// LateralSafetyEvaluator.kt:13-17（构造函数已预留参数，从未被外部传值）
class LateralSafetyEvaluator(
    private val minSafeTimeHeadway: Float = 2.0f,
    private val minStaticClearanceM: Float = 10.0f,
    private val minSafeTtcSeconds: Float = 2.5f,
    private val minTargetLaneClearanceM: Float = 20.0f
)
```

用户在设置页调整"前后距阈值"后，对实际安全评估**零效果**。

### 修复 — 车机端两步

**Step 1**：扩展 `OvertakeSettings`，增加可配阈值字段：

```kotlin
// OvertakeSettings.kt 新增字段
data class OvertakeSettings(
    // ... 现有字段 ...
    val minSafeTtcSeconds: Float = 2.5f,          // 后向 TTC 门限（对应超车风格三档）
    val minRearClearanceM: Float = 10.0f,         // 后向静态净空
    val minRearTimeHeadway: Float = 2.0f,         // 后向动态时距
    val minFrontClearanceM: Float = 20.0f,        // 目标车道前车净空
    val minEngageSpeedKmh: Int = 60,              // 准入车速
    val interruptCooldownMs: Long = 20_000L       // 接管惩罚冷却（移出硬编码）
)
```

**Step 2**：`loadOvertakeSettings()` 读取所有字段，并把超车风格（`overtake_mode` 0/1/2）映射到 TTC：

```kotlin
// UserSettingsRepository.kt — loadOvertakeSettings()
private fun loadOvertakeSettings(): OvertakeSettings {
    val mode = prefs.getInt(KEY_OVERTAKE_MODE, 1)   // 0激进 1常规 2保守
    val ttcByMode = when (mode) { 0 -> 1.8f; 2 -> 3.5f; else -> 2.5f }
    return OvertakeSettings(
        enabled              = prefs.getBoolean(KEY_OVERTAKE_ENABLED, true),
        standardCooldownMs   = prefs.getInt(KEY_REVERSE_COOLDOWN_S, 20) * 1000L,
        allowRightOvertake   = prefs.getBoolean("allow_right_overtake", false),
        minSafeTtcSeconds    = ttcByMode,
        minRearClearanceM    = prefs.getFloat(KEY_REAR_THRESH_VAL, 10.0f),
        minRearTimeHeadway   = prefs.getFloat(KEY_REAR_VREL_TIME, 2.0f),
        minFrontClearanceM   = prefs.getFloat(KEY_FRONT_THRESH_VAL, 20.0f),
        minEngageSpeedKmh    = prefs.getInt("overtake_min_speed", 60),
        interruptCooldownMs  = prefs.getInt("overtake_interrupt_cooldown_s", 20) * 1000L
    )
}
```

**Step 3**：`RelayEngine` 构造 `LateralSafetyEvaluator` 时传入设置值（需在 `onTelemetry` 路径中取最新 settings）：

```kotlin
// RelayEngine.onTelemetry() 修改
private fun onTelemetry(payload: String) {
    telemetryWatchdog.onTelemetry(SystemClock.elapsedRealtime())
    val car  = CarrotTelemetryParser.parse(payload)
    val navi = decoder.getFreshNaviState(2000L)
    _carStateFlow.value = car
    val settings = settingsRepository.settings
    // 把实时 settings 传给 evaluator（避免每次 new，改为 update 方法或可变参数）
    safetyEvaluator.updateThresholds(settings)
    _overtakeStatusFlow.value = stateMachine.tick(car, navi, settings)
    updateRampSpeed(car, navi)
}
```

`LateralSafetyEvaluator` 新增 `updateThresholds(settings: OvertakeSettings)` 方法更新内部字段。

**验证**：设置超车风格切换为"激进"，HUD Trace 中安全评估阻断原因里的 TTC 门限应变为 1.8 s。

## 9. ENG-1 — 未使用端口常量清理

> ⚠️ **原描述有误，已核实纠正（不删码）**。核实结果：
> - **4212** 是 C3 车道通道的 App 端口，**并非"从未使用"**：
>   `amap_navi.py:205 lane_remote_port=4212`、`:280 app_port=4212`、
>   `lane_protocol.py LANE_APP_PORT=4212`，并在 `amap_navi.py:1778` 实际
>   `sendto(..., 4212)` 广播车道数据；`_lane_recv_thread` 监听 4213 消费
>   `lane_runner`（`process_config.py:147` 仅 onroad 启动）。**删除会破坏车道视觉通道。**
> - **5210** 在当前代码中**不存在**（车机 `CarrotUdpClient` 只用 7705/7706）。
> - 车机 Reborn 目前**未消费** 4212/4213 车道结果（`CarrotUdpClient` 只收发
>   7705/7706）——这是「车道结果未回传车机」的功能缺口，**不是代码噪音**，
>   属车道视觉落地项，不应在此删除。
>
> **结论**：保留 4212/4213（车道通道），不移除任何端口常量。5210 无需处理（不存在）。

原建议（作废）：加注释说明保留原因或直接删除，减少维护者困惑。
