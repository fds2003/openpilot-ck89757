## Q-1 — `SharedData` 读写锁不一致

### 位置

```
amap_navi.py:24      lock = threading.Lock()   # 模块级全局锁
amap_navi.py:97-186  class SharedData           # 50+ 裸可变字段
```

### 问题

写路径（`_update_sensors`、`_update_command`、`_update_blinker`）正确加了 `with lock`；
读路径 `make_navi_message()`（1785 行）**直接裸读** `self.shared_data.xxx`，无任何锁保护。

```python
# _update_sensors — 写，有锁（正确）
with lock:
    self.shared_data.lidar_lblind = ...

# make_navi_message — 读，无锁（风险）
msg['lidar_behind_vdist_time'] = float(self.shared_data.behind_ttc)
msg['lidar_lbblind'] = bool(self.shared_data.lidar_lbblind)
```

20Hz 遥测写线程与 10Hz 广播读线程并发，`behind_ttc`（float）在 CPython 中赋值是原子的，但多字段组合读取仍可能读到"半更新"状态（写线程写完 `behind_ttc` 还没写 `lidar_lbblind` 时，读线程读到了不一致的一帧）。

### 修复方向

**方案 A（最小改动）**：`make_navi_message()` 开头用 `with lock` 把 `SharedData` 关键字段复制到局部变量，再构建 msg。

**方案 B（推荐）**：让写线程在每次传感器融合完成后，把完整快照放入 `data_queue`（已存在但未充分利用），`make_navi_message()` 从队列取最新快照，彻底消除共享状态读写竞争。

```python
# 写线程末尾
snapshot = SharedSnapshot(
    behind_ttc=self.shared_data.behind_ttc,
    lidar_lbblind=self.shared_data.lidar_lbblind,
    # ...
)
data_queue.put_nowait(snapshot)   # 非阻塞，丢最旧帧

# make_navi_message()
try:
    snap = data_queue.get_nowait()
except queue.Empty:
    snap = self._last_snapshot
self._last_snapshot = snap
```

## Q-2 — `make_navi_message()` God 函数 + 三份重复逻辑

### 位置

```
amap_navi.py:1785  make_navi_message()   ~250 行
amap_navi.py:2039  make_lidar_message()  ~40 行
amap_navi.py:2081  make_blinker_message() ~76 行
```

### 重复代码块

三个函数都包含完全相同的巡航状态推导逻辑（共 15 行，出现三次）：

```python
# 以下三段在三个函数中逐字重复
if self.sm.alive['selfdriveState']:
    selfdrive = self.sm['selfdriveState']
    self.shared_data.selfdrive_active = True if selfdrive.active else False
if self.shared_data.cruise_valid is not None:
    msg['active'] = self.shared_data.cruise_valid
cruise_enable = False
if self.shared_data.selfdrive_active is not None and self.shared_data.selfdrive_active:
    cruise_enable = True
if cruise_enable:
    msg['active'] = True
if not msg.get('engaged', False):
    msg['engaged'] = cruise_enable
```

此外三个函数均有：`isOnroad = self.params.get_bool("IsOnroad")` 读取、`radarState.leadOne` 解析（`make_navi_message` 和 `make_blinker_message` 各一份）。

### 修复方向

抽出两个辅助方法：

```python
def _build_base_fields(self) -> dict:
    """公共字段：IsOnroad、IP、port、device。"""
    return {
        'ip': self.local_ip_address,
        'port': self.listen_port,
        'device': 'op',
        'IsOnroad': self.params.get_bool('IsOnroad'),
    }

def _apply_cruise_state(self, msg: dict) -> None:
    """巡航状态推导（三函数共用，原地修改 msg）。"""
    if self.sm.alive['selfdriveState']:
        self.shared_data.selfdrive_active = bool(self.sm['selfdriveState'].active)
    if self.shared_data.cruise_valid is not None:
        msg['active'] = self.shared_data.cruise_valid
    cruise_enable = bool(self.shared_data.selfdrive_active)
    if cruise_enable:
        msg['active'] = True
    if not msg.get('engaged', False):
        msg['engaged'] = cruise_enable
```

三个 `make_*` 函数调用上述方法后只写各自增量字段，单函数长度可从 250 行降至 60 行以内。

## Q-3 — `hasattr()` 防御调用约 60 处，无统一适配层

### 位置

```
amap_navi.py — 全文，以 update_navi_carstate / make_navi_message 最密集
```

### 问题

```python
# amap_navi.py:1832-1841 — 仅 leadOne 就有 5 次 hasattr
if hasattr(radar_state, 'leadOne') and radar_state.leadOne \
   and hasattr(radar_state.leadOne, 'status') and radar_state.leadOne.status:
    if hasattr(radar_state.leadOne, 'dRel'):
        msg["drel"] = int(radar_state.leadOne.dRel)
    if hasattr(radar_state.leadOne, 'vLead'):
        msg["vlead"] = int(radar_state.leadOne.vLead * 3.6)
    if hasattr(radar_state.leadOne, 'vRel'):
        msg["vrel"] = int(radar_state.leadOne.vRel * 3.6)
    if hasattr(radar_state.leadOne, 'aRel'):
        msg["lead_accel"] = radar_state.leadOne.aRel
```

`hasattr` 泛滥说明 capnp schema 字段在运行时存在性不确定（跨版本兼容）。
问题：schema 新增/删除字段时，需要全文搜索所有 `hasattr` 点逐一确认，改动半径极大。

### 修复方向

在订阅入口封装一个轻量适配器，把 capnp 对象转为确定类型的 dataclass：

```python
from dataclasses import dataclass, field
from typing import Optional

@dataclass
class LeadState:
    status: bool = False
    d_rel: float = 0.0
    v_lead: float = 0.0
    v_rel: float = 0.0
    a_rel: float = 0.0

def _parse_lead(raw) -> LeadState:
    if raw is None or not getattr(raw, 'status', False):
        return LeadState()
    return LeadState(
        status=True,
        d_rel=getattr(raw, 'dRel', 0.0),
        v_lead=getattr(raw, 'vLead', 0.0) * 3.6,
        v_rel=getattr(raw, 'vRel', 0.0) * 3.6,
        a_rel=getattr(raw, 'aRel', 0.0),
    )
```

之后内部代码直接 `lead.d_rel`，`hasattr` 只在适配器中出现一次。

## Q-5 — `speed_hist.pop(0)` 在高频路径用 list

### 位置

```python
# amap_navi.py:90-95
def _update_hist(self, speed):
    self.speed_hist.append(speed)
    if len(self.speed_hist) > self.smooth_n:
        self.speed_hist.pop(0)   # ← O(n) 移位
    return sum(self.speed_hist) / len(self.speed_hist)
```

### 问题

`pop(0)` 在 list 上是 O(n)，`smooth_n` 默认为 5，虽然量级小，但该方法在 20~50Hz 的雷达速度估算路径中被高频调用。
文件顶部已有 `import collections`，`RadarSpeedEstimator` 自己却未使用。

### 修复

```python
# __init__
self.speed_hist = collections.deque(maxlen=self.smooth_n)

# _update_hist — pop(0) 和 len 判断均可删除
def _update_hist(self, speed):
    self.speed_hist.append(speed)   # deque 自动弹出最旧元素
    return sum(self.speed_hist) / len(self.speed_hist)
```

## Q-6 — `lb_drel/rb_drel` 两段覆盖，第一段写入永远无效

### 位置

```python
# amap_navi.py:1895-1918
# ── 第一段：fields 循环，idx==0 时写入 lb_drel/rb_drel ──
fields = ["lf_drel","lb_drel","rf_drel","rb_drel", ...]
for idx in sorted(all_lidar_ids):
    for field in fields:
        if idx in d and d[idx] is not None:
            key = field if idx == 0 else f"{field}{idx}"
            msg[key] = d[idx]            # lb_drel 在此被写入

# ── 第二段：无条件覆盖（注释写明"无条件覆盖"）──
for side in ("lb", "rb"):
    key = f"{side}_drel"
    main = getattr(self.shared_data, f"main_{side}_drel", None)
    if main is not None:
        msg[key] = round(abs(main) / 1000.0, 1)   # 覆盖第一段
    else:
        msg.pop(key, None)                          # 或删除第一段写入的值
```

**结论**：无论 `main_lb_drel` 是否存在，第一段对 `lb_drel/rb_drel`（idx==0）的写入结果：
- `main` 不为 None → 被覆盖，第一段无效
- `main` 为 None → 被删除，第一段无效

第一段写这两个字段是隐性死代码。

### 修复

在第一段 fields 列表中排除 `lb_drel`/`rb_drel`，明确只让第二段负责这两个字段：

```python
fields = ["lf_drel", "rf_drel", "lf_xrel", "lb_xrel", "rf_xrel", "rb_xrel"]
# lb_drel / rb_drel 由下方 main_* 覆盖逻辑统一负责
```

同时补充注释说明数据来源优先级，消除隐性逻辑。

## Q-7 — 异常处理过于宽泛

### 位置

全三个文件，密度最高在 `amap_navi.py`：

```python
# amap_navi.py:1028-1030
except Exception as e:
    print(f"Process packet {ip} error: {e}")
    print(data)                    # 原始字节，调试用，生产不应常态打印
```

```python
# amap_navi.py:1327
except Exception as e:
    print(json_obj)                # 吞掉传感器解析错误
```

**问题**：`json.JSONDecodeError`（格式错误包，丢帧继续）、`OSError`（socket 断开，需重建）、`AttributeError`（schema 字段缺失，需报告）三类异常语义完全不同，统一吞掉后排查时无法区分。

### 修复方向

按异常语义分层：

```python
try:
    json_obj = json.loads(data.decode())
except (json.JSONDecodeError, UnicodeDecodeError):
    # 格式错误帧：计数后丢弃，不影响后续处理
    self._malformed_count += 1
    return

try:
    self._update_blinker(json_obj, ip, old_info, now)
    self._update_command(json_obj, ip)
    self._update_sensors(json_obj, ip, old_info, now)
except KeyError as e:
    # schema 字段缺失：记录字段名，单次告警不停服
    cloudlog.warning(f"[amap_navi] missing field {e} from {ip}")
except Exception as e:
    # 真正意外：记录完整 traceback
    cloudlog.exception(f"[amap_navi] unexpected error from {ip}")
```
