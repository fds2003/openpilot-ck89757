## 0. 结论摘要

1. **车机端存在四个实现、三代协议**，不是"一个原版 + 一个复刻"的关系。
2. **官方 V1.3.6.9 无法安装到 API 19 车机**；真实基线是 minSdk 19 的兼容版（代码与官方包完全一致，2620 类）。
3. **C3 当前 HEAD（`ac57990`）因 S-4/S-5 回环绑定，与任何车机实现都不通**：接收 socket 全部绑 `127.0.0.1`，LAN 客户端无法登记，遥测无处可发。这是**先于所有协议问题的 P0**。
4. **C3 同时支持两套车机协议**（7706 旧 `carrotCmd` / 7705 新 `cmd`），但**遥测只发 7706**，因此只适配 Reborn，不适配原版 APK。
5. **没有任何车机实现把高德 TBT/算路发给 C3**；C3 的导航来自自身 `navd`。文档 04 §4.3.2 的"4211 导航引导数据流"从未实现。
6. **Reborn 按文档 14 的错误协议实现**（`ROAD_CATE`、10019、竖线车道串），对真实高德广播会出现 `isHighway=false` 与车道解析为空，**自动超车被永久阻断**。
7. **原版 APK 的端侧 ONNX 车道推理在 Android 4.4/i.MX6 上大概率不可用**（ORT 版本依赖），因此 4213 车道通道在实车上可能是空的；Reborn 放弃端侧视觉方向正确，但未补替代来源。
8. **三端各有一套决策逻辑**（APK / Reborn / C3 desire_helper + 自主 ATC），缺少互斥开关，存在双决策源冲突。

### 2.1 对四端实现的直接影响

| 约束 | 影响 |
|---|---|
| API 19 | 官方 V1.3.6.9（minSdk 21）**拒装**；兼容版通过降 minSdk + multidex 解决 |
| 32 位 ARM | APK 内置的 `arm64-v8a` ORT 为死重量；Reborn 仅编 `armeabi-v7a` |

| 1024×600 | APK 使用 dp 阈值适配（`OVERTAKE_FIXED_MIN_DETAIL_DP=250`、`ROAD_LIMIT_PANEL_MIN_HEIGHT_DP=250`） |

> **推论**：若 4.4 上 ONNX 不可用，原版 APK 的 4213 车道类型通道为**空载**，C3 的 `left_lane/right_lane` 只能依赖 C3 自身 `lane.py`。Reborn 无端侧视觉，也没有替代上报，安全门禁因此退化。

## 3. 四个车机实现

### 3.1 官方 V1.3.6.9 / 兼容版（同一代码基线）

- 组件：MainActivity、SettingActivity、OvertakeSettingActivity、NavSettingActivity、LogManagerActivity、UdpDeviceActivity、WxPayActivity、WebViewActivity；KeepAliveService；RestartReceiver、DebugReceiver。
- 网络：仅 `UdpService` 与 `UdpDeviceManager` 两个 socket 封装；全仓无 HTTP 业务请求。
- 端侧 AI：`assets/lane.onnx`（416×416，13.2MB）+ `com.carrot.lane.LaneDetect`。

### 3.2 高德桥接（Bridge）

- 仅 4 个类：`MainActivity`、`BridgeService`、`BootReceiver`、`R`。
- 职责：轮询 `http://<host>:8088/status` → 组装三类 JSON → UDP 上报。
- 无端侧推理，符合文档"轻量中继"路线。

### 3.3 Reborn

- 包 `tech.touka.amapnavi`，minSdk 19 / target 22，仅 `armeabi-v7a`。
- 无 ONNX、无相机帧拉取、无 4211/4213 通道。
- 自有决策引擎（`OvertakeStateMachine` + `LateralSafetyEvaluator` + `RouteLaneMarkingOracle`）。

## 4. C3 接收子系统

### 4.1 进程模型

`system/manager/process_config.py:142-146`：

```python
PythonProcess("carrot_man", "selfdrive.carrot.carrot_man", always_run)
#PythonProcess("amap_navi", ...)   # 已注释，避免双实例端口竞争
PythonProcess("lane", "selfdrive.carrot.lane", only_onroad)
```

`carrot_man` 内嵌 `AmapNaviServ()`，独占 UDP 与 `amapNavi` 发布者。

### 4.2 六个 UDP 线程

| 线程 | 绑定 | 作用 |
|---|---|---|
| `_discovery_responder_thread` | 4210 | 收 `c3_ping/discover`，登记 client（device=navi） |
| `_udp_recv_thread` | 4211 | 收 app/外设上行传感器与车道 JSON |
| `_lane_recv_thread` | 4213 | 收 `resp:"lane"` 车道类型 |
| `_headunit_cmd_recv_thread` | 7705 | 收新协议 `cmd` |
| `_data_deal_thread` | 发 7706 | 按 client 推遥测 |
| `carrot_man_thread` | 7706 | 收旧协议 `carrotCmd` |

### 4.3 命令汇流

```
7705 cmd ─► amap_navi.remote_cmd ─► carrot_man.get_data_amap_navi() ─┐
7706 carrotCmd ─► carrot_serv.update(json) ─────────────────────────┤
                                                                     ▼
                                                    carrot_serv.carrotCmd/Arg
                                                                     ▼
                                                    carrotMan (cereal)
                                                                     ▼
                              desire_helper.py:506  LANECHANGE / OVERTAKE
                              desire_helper.py:526  CANCEL
                              desire_helper.py:956  overtake_mode → TTC 1.8/2.5/3.5 s
```

`carrot_serv.command_handlers` 仅注册 `DETECT` 与 `SPEED_LIMIT`；变道由 `desire_helper` 直接消费 `carrotCmd`。

| KEY_TYPE | 内容 |
|---|---|
| 10001 | 导航/限速/测速/TBT/红绿灯（27 个字段） |

## 6. 当前 HEAD 可运行性判定

### 6.1 部署层（P0）

`ac57990` 的 S-4/S-5 加固把所有接收 socket 绑回环：

```
amap_navi.py:621   bind('127.0.0.1', 4210)
amap_navi.py:680   bind('127.0.0.1', 7705)
amap_navi.py:846   bind('127.0.0.1', 4213)
amap_navi.py:907   bind('127.0.0.1', 4211)
amap_navi.py:203   local_ip_address = "127.0.0.1"
carrot_man.py:652  bind('127.0.0.1', 7706)
carrot_man.py:734  bind('127.0.0.1', 12345)
carrot_man.py:912  bind tcp://127.0.0.1:7710
carrot_man.py:1050 host = '127.0.0.1'
```

遥测只发给 `self.clients`，而 client 只能由 4210/4211/7705 的学习逻辑登记。回环绑定使 **LAN 车机永远无法登记**。

> **判定：四种车机实现在当前 C3 HEAD 下全部无法通信（指令收不到、遥测发不出）。这是整体断路，不是某一段协议问题。**

### 6.2 契约层（假设放开 bind）

| 组合 | 指令 | 遥测 | 车道 | 转向灯 |
|---|---|---|---|---|
| 兼容版 APK + C3 | ✅ 7706 | ❌ C3 发 7706，APK 听 7705 | ✅ 4213 | ✅ 4211 |
| Bridge + C3 | — | ❌ 无 client 登记 | ✅ 4213 | — |
| Reborn + C3 | ✅ 7705 | ✅ 7706 | ❌ | ⚠ 仅随指令 |
| 官方 V1.3.6.9 | ❌ 装不上 | — | — | — |

## 7. 决策权冲突

| 决策者 | 依据 | 输出 |
|---|---|---|
| 原版 APK | 高德广播 + 视觉车道 + 遥测 + 三档参数 | `carrotCmd=LANECHANGE` |
| Reborn | 高德广播 + 遥测 + 单一参数集 | `cmd=LANECHANGE/SPEED_LIMIT/CANCEL` |
| C3 `desire_helper` | `carrotMan.carrotCmd` + 自身盲区 + `navInstruction` | 实际变道/转向 |
| C3 `update_auto_turn` | C3 自身 navd 的 TBT | 自主转向请求 |

**问题**：
- C3 自主 ATC 与车机意图之间无互斥开关；
- 车机 `CANCEL` 只能取消 `carrotMan` 链路，取消不了 C3 自身 ATC；
- 三侧冷却策略不一致：APK 6/10/15 s；Reborn 20/60 s；C3 `lane_change_interval`。

**建议**：明确"车机意图优先、C3 只做安全否决"，协同模式下关闭 C3 自主 ATC。

## 8. Reborn 具体不兼容点

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| 1 | `ROAD_CATE` vs APK `ROAD_TYPE` + 转换 | `AmapBroadcastDecoder.kt:40` vs `MainActivityAmapKt.java:114` | `isHighway=false`，超车永久阻断 |

| 4 | 无 `l_front_blind/r_front_blind` 门禁 | APK `LaneChangeSafetyCheckRaw` 返回 −2 | 少前角雷达闸 |
| 5 | 无 `blind_l/r`（−16）门禁 | 同上 | 少综合盲区闸 |

## 18. 4215 红绿灯通道处理（2026-11-06）

### 18.1 先纠正一个前提

- `08_AmapBridge_高德桥接_Android4.4车机专用版.apk` **没有源码**，无法直接删除其中的 4215 发送；
  重打包后签名不同，也无法覆盖安装。
- 但磁盘上存在可编译源码：`E:/code/adbridge-custin` 与 `E:/code/adbridge-cluster`
  （`com.carloc.adbridge`），同样发送 4211 / 4213 / **4215**。
- 核对后确认：adbridge **不发 `DETECT` 指令**，4215 是它**唯一**的红绿灯上行路径。
  删除 4215 会直接丢失红绿灯辅助功能。

### 18.2 因此改为"接上"，而不是删除

C3 新增 4215 接收线程，映射到 `carrot_serv.traffic_state`：

```
adbridge 4215 {"tl":"red|green","cd":18,"st":1,"dir":"left","src":"adbridge"}
  → amap_navi._traffic_light_recv_thread
  → shared_data.traffic_state / traffic_state_ts / traffic_light_cd
  → carrot_man.get_data_amap_navi()
  → carrot_serv.traffic_state
```

优先级与失效规则：
- `carrotCmd="DETECT"` 活跃（`traffic_light_count > 0`）时，DETECT 优先；
- 无 DETECT 时采用 4215，且要求数据新鲜（3s）；
- 超过 3s 未更新则清零，避免"绿灯残留"；
- 4215 同样经过 `_udp_trusted` 源信任检查。

## 21. 安全强度裁决：车内局域网是否需要 HMAC（2026-11-06）

### 21.1 结论

**不需要完整 HMAC。** 对车内封闭局域网，同网段/显式白名单 + 字段校验 + 序号单调
已经覆盖主要风险；HMAC 的复杂度与收益不匹配。

### 21.2 威胁模型

| 风险 | 存在性 | 现有控制 |
|---|---|---|
| 公网直达 | 否 | C3 仅车内局域网 |
| Web 8088 暴露 | 否 | 实际绑定 `127.0.0.1`，需 SSH 隧道 |
| ZMQ 7710 / 路由 7709 | 否 | 已绑 loopback |
| FTP | 默认关闭 | S-2 已收紧 |
| 同网段不可信设备注入 | 仅热点共享时 | 同网段/显式白名单 |
| 车机被装恶意 App | 存在 | **HMAC 无法防御**（密钥在车机内） |
| 物理接触 | 存在 | 协议层无法防御 |

关键判断：HMAC 防不住"车机本身被攻破"这一最现实威胁；它只防同网段未知设备，
而白名单已将范围收窄。

### 21.3 强度分级

| 方案 | 复杂度 | 建议 |
|---|---|---|
| 同网段 + 白名单 + 字段校验 + 序号单调 | 已完成 | **推荐** |
| 静态共享 token（非加密，仅准入） | 低 | 热点共享给乘客设备时可选 |
| HMAC-SHA256 + nonce + 时间窗 | 高，需三端同步 | **不推荐**，除非威胁模型变化 |

### 21.4 更值得投入的安全项

1. 车机端 `DebugReceiver`：原版 APK 导出 `com.carrot.amapnavi.DEBUG`，
   任意 App 可改参数/跑仿真；Reborn 已无此组件。
2. 原版 APK 为调试证书签名，可被同签名包替换。
3. 车内热点应启用密码，必要时开启 AP 隔离。
