## 三、Critical：F‑26‑01 端口契约仍双向交叉（25 号 2.1 未闭环）

### 3.1 实测证据

**车机端** `CarrotUdpClient.kt:31-32`：
```kotlin
const val PORT_TELEMETRY = 7706 // 监听遥测
const val PORT_CONTROL   = 7705 // 下发指令
```
**C3 端** `amap_navi.py:200-201`：
```python
self.navi_port = 7705         # 注释声称是"车机遥测收端口"
self.navi_remote_port = 7706  # 注释声称是"指令发往 C3 的端口"
```
**C3 端实际使用位置**：
- `:640` 指令监听：`s.bind(('0.0.0.0', self.navi_remote_port))` → **绑 7706**
- `:1613` 遥测发送：`sock.sendto(navi_dat, (ip, self.navi_port))` → **发 7705**
- `:1612` 遥测另发：`sock.sendto(navi_dat, (ip, port))`，`port` 来自发现注册的 `broadcast_port=4210` → **发 4210**

### 3.2 双向对照表

| 方向 | 发送方 → 目标端口 | 接收方监听的端口 | 结果 |
|:---|:---|:---|:---:|
| 遥测 C3 → 车机 | C3 发 **7705**（另发 4210） | 车机监听 **7706** | ❌ 断 |
| 指令 车机 → C3 | 车机发 **7705** | C3 监听 **7706** | ❌ 断 |

**两个方向同时错位**，与整改前的错位方式完全对称。

### 3.3 根因：双重取反

493e8dd 把 C3 的 `navi_port`/`navi_remote_port` **数值对调**，但**没有对调代码中 bind/send 的变量引用**；与此同时车机端常量也**同向翻转**（原 7705/7706 → 新 7706/7705）。两端各翻一次、方向相同 → **相对关系不变，仍然交叉**。这是"修了一半"的典型形态。

### 3.4 最小修复（只改 C3 两行数值即可）

**方案 A（推荐，改动最小）** —— 恢复 C3 数值语义，使变量引用重新自洽：
```python
# selfdrive/carrot/amap_navi.py:200-201
self.navi_port = 7706          # C3 向车机发送遥测的目标端口（车机监听 7706）
self.navi_remote_port = 7705   # C3 监听车机指令的端口（车机发送 7705）
```
改后自动成立：
- `:640` 绑 `navi_remote_port`=7705 ✓（车机发 7705）
- `:1613` 发 `navi_port`=7706 ✓（车机听 7706）

**方案 B** —— 保持数值不动，对调两处引用（`:640` 改绑 `navi_port`，`:1613`/`:1615` 改发 `navi_remote_port`）。

> 注意 `:1612` 的 `(ip, port)`（4210）是发现注册端口，车机不在 4210 收遥测，属无效发包，可保留或删除，不影响闭环。

## 四、Major 残留问题

### F‑26‑02 激光雷达缺失时仍 fail‑open
`amap_navi.py` 中 `ttc = min(ttc_list) if ttc_list else 99.0`；无任何雷达目标/雷达整体掉线时即为 `99.0`。
`desire_helper.py:923-934` 仅在 `self.sm.alive['amapNavi']` 为假时把 `behind_ttc` 置 0.0 阻断；而 `carrot_man` 是 `always_run`，消息几乎总存活 → **雷达掉了也放行**。
**建议**：在 `public_amap_navi` 里用雷达存在标志门控（`lidar_l/lidar_r` 或客户端计数），无雷达时输出 `lidarBehindVdistTime = 0.0`（哨兵=阻断）；如需兼容"未装雷达"的用户，用 `Params` 开关显式声明，默认安全侧。

### F‑26‑03 单调序号门控导致车机重启后指令永久锁死
车机 `CarrotUdpClient.kt:41` `sequenceId = AtomicInteger(1)` 为**进程内变量**，车机 App 重启后从 1 重新计数；C3 `amap_navi.py:1009-1010` 仅接受 `idx > cmd_index` 且 `cmd_index` **从不复位** → 重启后所有指令被静默丢弃，直到序号重新超过历史最大值。
**建议**：`app_ip` 变化、或超过 N 秒无指令时复位 `cmd_index = -1`；或改用 `(app_ip, seq)` 组合键 + 时间窗口判重，而非纯单调。

### F‑26‑04 `CANCEL` / `SPEED_LIMIT` 下游无消费者（25 号 3.4 宣称不实）
25 号称"支持 `CANCEL_LANE_CHANGE` 撤销，紧急可刹停变道"。实测：C3 仅把 `CANCEL_LANE_CHANGE` 映射成字符串 `"CANCEL"`，但
- `desire_helper.py:506` 只识别 `"LANECHANGE"` / `"OVERTAKE"`；
- `carrot_serv.py:354-360` 的 `command_handlers` 只有 `"DETECT"`。
→ **`CANCEL` 无任何处理器，是空操作**。
同理车机 `RelayEngine.kt:185-190` 用 `SPEED_LIMIT` 下发巡航/匝道限速，C3 也**无 `SPEED_LIMIT` 处理**（全仓 grep 仅在车机侧出现）。
**建议**：在 `desire_helper` 的命令分支增加 `"CANCEL"` → `self.carrot_lane_change_count = 0; self.lane_change_state = LaneChangeState.off`；在 `carrot_serv` 增加 `SPEED_LIMIT` handler（写 `v_cruise` 相关参数）。若暂不实现，**必须从 25 号报告中删除这两条宣称**，避免验收口径失真。
